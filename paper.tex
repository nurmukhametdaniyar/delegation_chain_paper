\begin{abstract}
Autonomous software agents built on large language models increasingly invoke
tools and services across organizational boundaries, frequently via the Model
Context Protocol (MCP). When an agent at one organization invokes a tool at
another, the receiving organization currently has no cryptographically
verifiable guarantee that the invocation was authorized, that the specific
parameter values were sanctioned rather than just the action type, or that the
authorization chain leading to the call was not tampered with. Existing
authorization protocols address subsets of these properties but do not
jointly satisfy them. We propose DelegationChain, a protocol providing
parameter-bound, aggregatable authorization proofs that a receiving
organization verifies locally, without a synchronous call to the issuing
authority on the dominant path. The protocol uses BLS12-381 signatures
with proof-of-possession, a recursive chain digest construction enabling
compact aggregate signatures across $N$-hop delegations, a typed declarative
policy expression language with a polynomial-time, sound scope
containment check, and a federated
identity registry model that permits interoperation between mutually
distrusting organizations without a shared trust anchor. We define a threat
model organized into six families of attack, describe the protocol's
cryptographic and operational components, and present a preliminary security
analysis. We discuss limitations, including the absence at this stage of an
empirical performance evaluation and machine-checked security proofs, and
outline the path to a full evaluation including symbolic protocol verification
and a Rust reference implementation.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Software agents built on large language models are increasingly deployed in
configurations where they invoke external tools and delegate sub-tasks to
other agents. The Model Context Protocol \citep{anthropic-mcp}, introduced in
late 2024, has emerged as a widely-adopted standard for this interaction
pattern. As deployment scales, an architectural pattern is becoming
common: agents operated by one organization invoke tools or delegate
work to agents operated by another.

Cross-organizational agent invocation creates an authorization problem that
existing infrastructure does not adequately address. Consider an agent at
Organization A, acting on behalf of a human principal, that needs to invoke
a payment-processing tool at Organization B. Organization B's tool must
decide whether to honor the request. To do so safely, B needs verifiable
answers to four questions: \emph{(i)} did the request actually originate
from an authorized agent at A, rather than from an attacker impersonating
that agent; \emph{(ii)} was the agent operating within the scope its
human principals authorized, rather than acting beyond its delegated
authority; \emph{(iii)} were the specific parameter values supplied --- the
amount, the recipient, the file path --- sanctioned by the authorization
chain, or has an intermediate party substituted them; and \emph{(iv)} has
the authorization chain itself been preserved intact, or has some step in
the chain been forged, dropped, or reordered.

Existing protocols address subsets of these questions but do not jointly
satisfy them. OAuth 2.1 \citep{oauth21} proves an agent's identity to a
resource server but does not bind authorization to specific parameter
values, requires a synchronous call to the authorization server on the
verification path, and cannot represent attenuated delegated authority across
organizational boundaries. Macaroons \citep{birgisson2014macaroons} provide
attenuated capability delegation with policy caveats, but use HMAC-based
verification with shared secrets, which does not extend cleanly across
organizations that do not share infrastructure. SPIFFE \citep{spiffe} provides
workload identity within a trust domain but does not include parameter binding
or delegation chains. UCAN \citep{ucan-spec} extends capability delegation to
public-key settings and, in version 1.0, specifies a policy language over
command arguments, but it defines no containment relation between
capabilities and does not address MCP integration or BLS aggregation. Recent
MCP-specific proposals such as AgentBound \citep{buhler2026agentbound}
provide single-organization runtime enforcement, and measurement work
\citep{zhou2026mcpauth, maloyan2026breaking} establishes the size of the
gap, but neither provides cross-organizational cryptographic proofs. The Agent Identity Protocol \citep{prakash2026aip} introduces
invocation-bound capability tokens for cross-protocol delegation but does not
incorporate aggregatable signatures, the formal policy language we present,
or the federated identity infrastructure.

This paper proposes DelegationChain, an authorization protocol designed
specifically for cross-organizational agent invocation. We describe a
protocol design intended to combine, in a single coherent system, several
properties that prior systems have addressed individually: public-key
cryptographic verification across organizations without a shared root of
trust; binding of authorization to exact parameter values, not merely action
types; compact aggregate signatures across multi-hop delegation chains; and
verification that requires no synchronous calls to the issuing authority
during the dominant path. The protocol is constructed on BLS
signatures \citep{boneh2001bls, ietf-bls-signature} over the BLS12-381
curve \citep{ietf-pairing-curves}, with proof-of-possession
registration, a recursive chain digest construction enabling chain integrity
under aggregation, a typed declarative policy language with termination
and containment guarantees, and a federated organizational registry
model.

\paragraph{Contributions.}
This paper makes four contributions. First, we define a threat model for
cross-organizational agent invocation organized into six families of
attack, spanning protocol-level attacks, identity infrastructure
attacks, and threats specific to LLM-based agent systems such as prompt
injection within permitted policy, and separating the families the
protocol prevents from the one it merely bounds
(\cref{sec:threat-model}). Second, we specify the protocol's cryptographic
core, wire format, verifier algorithm, and identity infrastructure
(\cref{sec:protocol,sec:identity}) to a level of detail sufficient for a
reference implementation, though not for byte-exact interoperability
between independent ones, which would require the normative
specification \cref{sec:protocol} declines to fix. Third, we introduce a typed
declarative policy expression language with a formal grammar, a
polynomial-time scope containment procedure that is sound with respect
to a semantic subset relation, and a proof of evaluator termination
(\cref{sec:policy}),
which we argue is sufficiently expressive for realistic enterprise
authorization while remaining free of the injection and denial-of-service
hazards of general-purpose policy languages. Fourth, we provide a
preliminary security analysis (\cref{sec:security}) reducing the protocol's
core security properties to standard cryptographic assumptions.

\paragraph{Scope and limitations.}
This paper is a design contribution. We do not yet present empirical
performance measurements from a reference implementation, machine-checked
security proofs, or results from symbolic protocol verification tools such
as Tamarin or ProVerif. Each of these is in progress and is required before
the protocol is ready for production use. We discuss the planned evaluation in
\cref{sec:limitations}. The contribution of this paper is the design and
its preliminary analysis; the full evaluation is future work.

\Cref{sec:protocol} describes the cryptographic core: chain digest

\section{Background}
\label{sec:background}

This section reviews the cryptographic and protocol background required to
follow the design. Readers familiar with pairing-based cryptography and MCP
may skim.

\subsection{Model Context Protocol}
\label{sec:bg-mcp}

The Model Context Protocol (MCP) \citep{anthropic-mcp} is a JSON-RPC-based
protocol standardizing how AI agents discover and invoke external tools.
An MCP \emph{host} (typically an LLM-based agent) communicates with one or
more MCP \emph{servers}, each exposing a set of tools. Tools are described
by name, a typed parameter schema, and documentation. The host requests a
tool invocation by sending a JSON-RPC message specifying the tool name and
parameter values; the server executes the tool and returns the result.

MCP's design assumes that the host and server are mutually trusted, an
assumption appropriate for the single-organization deployments common in
its early adoption. As MCP deployments scale to cross-organizational
configurations, this assumption becomes untenable. A server invoked by an
unknown agent has no cryptographic basis on which to decide whether the
invocation is authorized. The protocol's current security guidance relies
on transport-layer authentication (typically OAuth) which addresses caller
identity but not the broader authorization questions enumerated in
\cref{sec:introduction}. The gap is not hypothetical: a measurement study
of real-world remote MCP servers \citep{zhou2026mcpauth} identified 7,973
live servers and found that 40.55\% expose tools without any
authentication at all, and that among the OAuth-enabled servers it was
able to probe, every one exhibited at least one authentication flaw.

\subsection{BLS Signatures and Aggregation}
\label{sec:bg-bls}

The Boneh-Lynn-Shacham (BLS) signature scheme \citep{boneh2001bls} is a
signature scheme constructed from bilinear pairings on elliptic curves.
The scheme is specified for interoperable use by
\citet{ietf-bls-signature}; the curve we adopt, BLS12-381, is specified
separately by \citet{ietf-pairing-curves}. On that curve, signatures
consist of
a single point in $\G{2}$ (96 bytes compressed) and public keys consist
of a single point in $\G{1}$ (48 bytes compressed). Signing requires one
scalar multiplication; verification requires evaluation of a bilinear
pairing.

The property that makes BLS signatures particularly attractive for our
setting is \emph{signature aggregation}. Given signatures
$\sigma_1, \ldots, \sigma_n$ on distinct messages
$m_1, \ldots, m_n$, their sum $\sigma_{\text{agg}} = \sum_i \sigma_i$ is
itself a valid object in $\G{2}$, and its validity with respect to the
signing public keys and messages can be checked via a single
multi-pairing operation \citep{boneh2018compact}.

The precondition for aggregate unforgeability under proof-of-possession
is that the \emph{messages} be distinct; the signers need not be. The
distinction matters for delegation chains, where the same agent may
legitimately appear at more than one hop --- a chain
$A \rightarrow B \rightarrow A$ is a normal pattern, not an attack ---
and where the recursive chain digest of \cref{sec:protocol-digest}
guarantees distinct messages at every hop by construction, since each
$m_k$ commits to $m_{k-1}$. Aggregation has two consequences
relevant to our design.

First, the bandwidth required to transmit $n$ signatures is reduced to a
single $\G{2}$ element, regardless of $n$. For our delegation chains, this
means a chain of arbitrary length carries a fixed 96-byte aggregate
signature rather than $96n$ bytes of individual signatures.

Second, the computational cost of verification is reduced relative to
verifying $n$ signatures independently. We address the precise cost in
\cref{sec:protocol-verification}; here we note that the cost is not, as is
sometimes stated, asymptotically $O(1)$ in the number of signers when the
signers sign distinct messages. The honest characterization, which we
adopt throughout, is that aggregation provides significant constant-factor
savings via Miller loop sharing in the underlying multi-pairing
implementation.

BLS aggregation is vulnerable to rogue-key attacks unless the registration
of public keys requires proof-of-possession of the corresponding secret
keys \citep{boneh2018compact}. We address this in \cref{sec:identity-pop}.

\subsection{Capability-Based Authorization}
\label{sec:bg-capabilities}

The protocol design draws on the capability-based security tradition
\citep{miller2006robust}. In a capability system, authority is represented
by unforgeable tokens (capabilities) that the holder can present to obtain
access. Capabilities can be \emph{attenuated}: a holder may produce a
restricted version of a capability and delegate the restricted version to
another party, without being able to grant authority exceeding what they
themselves hold.

Macaroons \citep{birgisson2014macaroons} apply this model to web
authorization. A macaroon is an HMAC chain in which each link adds
``caveats'' --- predicates restricting the macaroon's use. First-party
caveats are checked by the target service itself, and verification
recomputes the HMAC chain using a secret that the target service knows.

Macaroons do address the cross-domain case, through \emph{third-party
caveats}. A caveat may name a principal other than the target service;
to use the macaroon, the holder must obtain a \emph{discharge macaroon}
from that principal attesting that the caveat is satisfied, and present
it alongside. The discharge is cryptographically bound to the macaroon
it discharges, and the target service verifies it without sharing a
secret with the third party. It is therefore not correct to say that
Macaroons cannot cross organizational boundaries, and we do not say so.

The difference that matters for our setting is where the work happens.
A third-party caveat costs a round trip: before presenting the macaroon,
the holder must contact each named third party and collect a discharge,
and the third party must be reachable at that moment. DelegationChain
places the equivalent authority in signatures the verifier checks
directly against registry-resolved public keys, with no discharge
collection step on the request path.

UCAN \citep{ucan-spec} extends capability attenuation to public-key
settings using ECDSA or Ed25519 signatures and a JWT-like token format.
UCAN is designed for Web3 contexts and lacks features specific to our
setting: signature aggregation, a containment relation between
capabilities (UCAN 1.0 does specify a policy language over command
arguments), and MCP transport binding.

DelegationChain inherits the conceptual framework of attenuated
capabilities from this tradition. Our contribution is the combination of
public-key verification (extending Macaroons' attenuation model across
organizational boundaries), signature aggregation (improving over the
per-hop linear growth of UCAN tokens), an explicit policy language with
termination and containment guarantees, and a federated identity
infrastructure.

\section{Threat Model}
\label{sec:threat-model}

This section defines the threat model under which DelegationChain operates.
We state the protocol's assets, the assumed adversary capabilities, the
threats we defend against, the threats we explicitly do not defend against,
and the security properties we seek to provide.

\subsection{Assets and Principals}
\label{sec:threat-assets}

The assets we seek to protect are: \emph{(i)} the integrity of tool
invocations, in the sense that an accepted invocation faithfully
represents the authorization granted by the originating principals;
\emph{(ii)} the provenance of authorization chains, in the sense that the
chain delivered to a verifier accurately records the parties that authorized
each step; and \emph{(iii)} the integrity of audit records derived from
accepted chains.

The principals participating in the protocol are: the \emph{human operator},
who initiates a request and whose authority is the ultimate source of
permissions; the \emph{orchestrator agent}, which receives the initial
authorization and may delegate to other agents; \emph{specialist agents},
which receive delegated authority and either invoke tools directly or
delegate further; the \emph{tool} or \emph{MCP server}, which receives
authorization chains and decides whether to honor invocations; the
\emph{signing service}, a hosted component that holds an agent's private
key and applies policy enforcement before signing; the \emph{approval
service}, which obtains human approval for actions requiring it and signs
approval receipts; and the \emph{registry}, which issues identity
certificates binding agents and services to public keys.

\subsection{Adversary Capabilities}
\label{sec:threat-adversary}

We model a probabilistic polynomial-time adversary with the following
capabilities. The adversary can observe and modify all network traffic
between principals (a standard Dolev-Yao adversary on the network). The
adversary can compromise an agent's runtime environment, gaining the
ability to instruct the signing service to sign messages of the
adversary's choice within the scope permitted by policy. The adversary can
inject content into agent inputs to attempt prompt injection attacks. The
adversary cannot, by default, compromise hardware security modules, the
signing service infrastructure, the approval service infrastructure, the
registry, or human approvers' devices; threats involving these
compromises are addressed separately and explicitly.

\subsection{Threats Within Scope}
\label{sec:threat-scope}

The threats in scope fall into six families. Variants within a family
share a \emph{target} --- what the attacker is trying to subvert --- and
not necessarily a defense; \cref{sec:security-threats} maps each variant
individually to the theorem or mechanism that answers it. Threats are
labelled for cross-reference in the security analysis
(\cref{sec:security}).

We divide them by what the protocol actually does about them rather than
by family. \Cref{sec:threat-within-scope} lists what it \emph{prevents}.
\Cref{sec:threat-bounded} lists what it only \emph{bounds}: the attack
remains possible, and the protocol limits what it can achieve. Both are
in scope, in the sense that the design is answerable for them, but a
reader who took the second group for the first would credit the protocol
with guarantees it does not provide. The division cuts across one
family --- \threatref{4a} is bounded while the rest of T4 is prevented
--- and we would rather have an untidy grouping than a tidy overclaim.

\subsubsection{Threats the protocol prevents}
\label{sec:threat-within-scope}

\paragraph{T1 --- Forgery of tokens and chains.}

\threat{1a}{Token forgery.} An adversary attempts to produce a valid
authorization token without holding the corresponding signing key.

\threat{1b}{Chain forgery and reordering.} An adversary attempts to
construct an authorization chain that was not produced by the legitimate
delegation sequence, including reordering hops, dropping hops, or
inserting unauthorized hops.

\paragraph{T2 --- Misrepresentation of granted authority.}
The two variants share a target --- the authorization that reaches the
verifier is not the authorization that was granted --- but not a
defense: \threatref{2a} is defeated by the signature over the parameter
encoding, \threatref{2b} by the containment check.

\threat{2a}{Parameter substitution.} An adversary, positioned between a
signer and a verifier, attempts to alter parameter values in an
authorized invocation (e.g., changing the destination of a transfer)
while preserving the appearance of valid authorization.

\threat{2b}{Scope escalation.} An agent attempts to delegate more
authority than it was itself granted.

\paragraph{T3 --- Reuse of valid tokens.}

\threat{3a}{Replay across sessions.} An adversary captures a valid
authorization chain and attempts to use it after its intended validity
window has expired.

\threat{3b}{Replay within validity window.} An adversary captures a
valid authorization chain and attempts to use it more than once within
its validity window.

\threat{3c}{Cross-context token reuse.} An adversary attempts to reuse a
token issued in one context (e.g., for a delegation) as if it had been
issued in another context (e.g., for an invocation).

\paragraph{T4 --- Subversion of the approval path.}
The remaining variant of this family, \threatref{4a}, is bounded rather
than prevented and appears in \cref{sec:threat-bounded}.

\threat{4b}{Approval routing attack.} An agent routes approval requests
to a permissive approval service when policy requires a stricter one.

\threat{4c}{Approval reuse across invocations.} An adversary attempts to
reuse a valid approval receipt with an invocation different from the one
approved.

\threat{4d}{Stale approval after parameter modification.} An adversary
attempts to modify invocation parameters after approval has been
obtained.

\paragraph{T5 --- Attacks on the identity infrastructure.}

\threat{5a}{Rogue-key registration.} An adversary attempts to register a
public key for which it does not hold the secret key, in order to inject
controlled keys into aggregate signatures.

\threat{5b}{Compromised registry signing key.} An adversary obtains a
registry's root signing key and issues fraudulent certificates.

\threat{5c}{Revocation suppression.} An adversary suppresses revocation
information from reaching verifiers, extending the window during which
compromised credentials remain accepted.

\threat{5d}{Certificate substitution.} An adversary substitutes a
different certificate for the same identity during the registration or
resolution process.

\subsubsection{Threats the protocol bounds but does not prevent}
\label{sec:threat-bounded}

The protocol limits the damage the following attacks can do, but does
not prevent them, and we do not claim that it does.
\Cref{sec:security-threats} states what the bound is in each case.

\paragraph{T4 --- Subversion of the approval path (one variant).}

\threat{4a}{Compromised approval service.} An adversary obtains the
signing key of an approval service and issues fraudulent approvals. The
protocol cannot prevent this: a valid signature under a registered
approval key is, by construction, a valid receipt. What it does is
contain the consequences. Approval receipts are verified separately from
the chain aggregate (\cref{sec:protocol-approvals}), so a compromised
approval service cannot forge delegation chains, cannot enlarge any
agent's scope, and cannot attest to anything beyond what it was already
trusted to attest to; the blast radius is exactly the set of invocations
that policy routes through that service. Detection and recovery belong
to the identity infrastructure --- transparency log monitoring and
rotation (\cref{sec:identity}).

\paragraph{T6 --- Misuse of an agent within its own policy.}

\threat{6a}{Prompt injection within policy.} An adversary, controlling
content fed to an agent, induces the agent to take actions that are
within the agent's permitted policy but contrary to the principal's
intent.

\threat{6b}{Confused deputy in delegation.} An agent is induced to sign
a delegation token favoring an adversary by manipulation of the inputs
the agent uses to construct delegation decisions.

\subsection{Threats Outside Scope}
\label{sec:threat-outside}

The following threats are explicitly outside our scope. Defending against
them requires mechanisms orthogonal to the protocol.

A fully compromised signing service can produce signatures on any
messages within an agent's policy; the protocol cannot prevent this and
relies on operational hardening (HSM-based key custody, monitored
access). Compromise of an approval service is treated in
\cref{sec:threat-bounded} rather than here, because the protocol does
bound its effect even though it cannot prevent it. Side-channel attacks on cryptographic implementations are
out of scope; we rely on the security properties of well-audited BLS
libraries such as \texttt{blst}. Attacks on the human approver's device or
authentication mechanism are out of scope; the protocol assumes a trusted
path between the approval service and the human. Denial-of-service attacks
on network infrastructure are out of scope. Post-quantum security is out
of scope for this version; BLS12-381 is not post-quantum secure, and
migration to a post-quantum scheme is left to future work.

\subsection{Security Properties Sought}
\label{sec:threat-properties}

We seek to provide the following security properties, each of which is
formally stated and argued in \cref{sec:security}:

\begin{description}
    \item[Authenticity.] Authorization tokens are unforgeable: no PPT
    adversary lacking access to a signing key can produce a token that
    verifies under the corresponding public key, except with negligible
    probability.
    \item[Parameter binding.] A token authorizing an invocation with
    parameter values $P$ is invalid for any parameter values $P' \neq P$.
    \item[Chain integrity.] The aggregate signature over a delegation
    chain covers the entire chain content; modification, reordering,
    truncation, or extension of the chain invalidates the aggregate.
    \item[Scope monotonicity.] In any valid chain, the session scope is
    contained in a policy the verifier has pinned for the issuing
    organization, and the scope at hop $k+1$ is contained in the scope
    at hop $k$.
    \item[Non-repudiation.] Neither party to a verified action can
    plausibly deny it, assuming honest signing key management.
    \item[Bounded revocation propagation.] Once a registry has issued a
    revocation assertion, the additional window before verifiers cease
    accepting tokens under the affected certificate is bounded by a
    configurable parameter (default: 120 seconds). Detection of the
    compromise and its reporting to the registry precede this window and
    are properties of the deploying organization's monitoring rather
    than of the protocol. The protocol bounds propagation, not total
    exposure.
\end{description}

\section{Protocol Design}
\label{sec:protocol}

This section presents the cryptographic core of DelegationChain: the
participants, the token types, the chain digest construction enabling
aggregate signatures across delegations, the encoding of parameter-bound
authorization, the handling of approval receipts, and the verifier
algorithm. We describe the design at a level of detail sufficient to
support the security analysis of \cref{sec:security} and to motivate the
implementation effort. Bit-level details beyond those given here ---
field numbering within each structure, and the exact byte layout of the
wire format --- are not fixed by this paper and would be settled by a
normative specification, which does not yet exist.

\subsection{Participants and Tokens}
\label{sec:protocol-participants}

A DelegationChain authorization chain has the following participants, in
the order they contribute to the chain. The \emph{issuer}~$I$ is the
registry or identity authority that issues an initial session token to
the orchestrator agent at the start of an authorized session. The
\emph{orchestrator}~$A_1$ is the agent that receives the session token
and initiates the workflow. Intermediate \emph{specialist
agents}~$A_2, \ldots, A_{N-1}$ may be delegated sub-tasks. The
\emph{invoking agent}~$A_N$ is the agent that finally invokes a tool at
the verifier. The \emph{verifier}~$V$ is the receiving tool or MCP
server. When policy requires human approval, an \emph{approval service}
contributes a separately-signed receipt.

The chain contains three token types. The \emph{session token},
signed by the issuer, authorizes the orchestrator to operate within a
scope for a bounded duration. \emph{Delegation tokens}, signed by
intermediate agents $A_k$ for $1 \le k < N$, attenuate authority and
pass it to the next agent. The \emph{invocation token}, signed by the
final agent $A_N$, binds the invocation to specific tool, action, and
parameter values. The chain delivered to the verifier consists of all
token bodies plus a single aggregate signature in $\G{2}$.

\subsection{Cryptographic Primitives}
\label{sec:protocol-primitives}

We use BLS12-381 \citep{ietf-pairing-curves} with the
minimal-pubkey-size variant of \citet{ietf-bls-signature}: public keys are
points in $\G{1}$ (48 bytes compressed), signatures are points in $\G{2}$
(96 bytes compressed), and the pairing maps $\G{1} \times \G{2}$ to
$\Gt$. Hash-to-curve uses RFC 9380 with suite
\texttt{BLS12381G2\_XMD:SHA-256\_SSWU\_RO\_}. SHA-256 is used for all
non-curve hashing, including the chain digest construction.

Signing key $\sk \in \Zq$, public key $\pk = \sk \cdot g_1 \in \G{1}$.
For message $m \in \{0,1\}^*$, $\Sign(\sk, m) = \sk \cdot \HashG(m) \in
\G{2}$. Verification checks $\pair{g_1}{\sigma} \overset{?}{=}
\pair{\pk}{\HashG(m)}$. For signatures
$\sigma_1, \ldots, \sigma_n$ on distinct messages --- which the chain
digest construction of \cref{sec:protocol-digest} guarantees, and which
does not require the signers to be distinct ---
the aggregate $\sigma_{\text{agg}} = \sum_i \sigma_i \in \G{2}$ is
verified by a multi-pairing check (\cref{sec:protocol-verification}).

All participants register public keys through a process that includes
proof-of-possession (\cref{sec:identity-pop}), preventing rogue-key
attacks against the aggregate.

\subsection{Chain Digest Construction}
\label{sec:protocol-digest}

The central cryptographic construction is a recursive digest chain
binding each hop to all prior hops. We use domain separation tags to
ensure tokens of different types cannot be confused (preventing
cross-context reuse, \threatref{3c}). Tags are 8-byte ASCII strings with a
null terminator: \texttt{TAG\_SES} for sessions, \texttt{TAG\_DEL} for
delegations, \texttt{TAG\_INV} for invocations.

Let $\Canon(\cdot)$ denote canonical encoding (deterministic CBOR per
RFC 8949 §4.2.1, with the additional rules summarized in
\cref{sec:protocol-encoding}).

\paragraph{Session message.}
The issuer signs:
\begin{equation}
m_0 = H(\text{TAG\_SES} \,\|\, \Canon(\text{SessionBody}))
\end{equation}
where SessionBody contains the issuer's identifier
(\texttt{issuer\_id}), the orchestrator's identifier and public key
(\texttt{subject\_id}, \texttt{subject\_pk}), a session identifier, a
hash committing to the governing policy (\texttt{policy\_hash}), a
scope expression, issue and expiry timestamps, and a fresh nonce.

\paragraph{Delegation messages.}
For each intermediate hop $A_k$ with $1 \le k < N$:
\begin{equation}
m_k = H(\text{TAG\_DEL} \,\|\, m_{k-1} \,\|\, \Canon(\text{DelegationBody}_k))
\end{equation}
where DelegationBody$_k$ contains the delegator's identifier and public
key (\texttt{delegator\_id}, \texttt{delegator\_pk}), the delegatee's
identifier and public key (\texttt{delegatee\_id},
\texttt{delegatee\_pk}), the attenuated sub-scope, a hop index, the
parent session identifier, expiry, and a fresh nonce. The delegator's
identifier is carried explicitly so that a verifier can resolve the
signer's certificate from the body it is checking, rather than having
to reach back into the preceding token. The critical property is that
$m_k$ commits to $m_{k-1}$ via the hash, recursively committing to the
entire chain history.

\paragraph{Invocation message.}
The final hop $A_N$ signs:
\begin{equation}
m_N = H(\text{TAG\_INV} \,\|\, m_{N-1} \,\|\, \Canon(\text{InvocationBody}))
\end{equation}
where InvocationBody contains the invoker's identifier and public key
(\texttt{invoker\_id}, \texttt{invoker\_pk}), the target tool
and action identifiers, the canonically encoded parameter values, a
hash of the parameters (defense-in-depth against encoding bugs), an
optional approval receipt, and timing and nonce fields.

\paragraph{Aggregate signature.}
Each participant signs its corresponding message with its private key,
producing $\sigma_k = \Sign(\sk_k, m_k)$ for $k = 0, 1, \ldots, N$. The
aggregate signature transmitted to the verifier is
\begin{equation}
\sigma_{\text{agg}} = \sigma_0 + \sigma_1 + \cdots + \sigma_N \in \G{2},
\end{equation}
which has constant size 96 bytes regardless of $N$. The aggregate is
accumulated along the chain: each participant receives the running
aggregate from its predecessor, adds its own contribution, and forwards
the sum. This does not keep the individual contributions secret --- an
adversary on the network (\cref{sec:threat-adversary}) observes
successive partial sums and recovers any $\sigma_k$ by subtraction ---
and nothing in the security argument requires that it should.
\Cref{thm:chain-integrity} rests on the digest recursion, not on the
secrecy of the summands.

\paragraph{Role distinguishability by position.}
The verifier reconstructs the $m_k$ values from received token bodies
using the tag determined by token position: \texttt{TAG\_SES} for the
session token, \texttt{TAG\_DEL} for each intermediate delegation
token, and \texttt{TAG\_INV} for the invocation token. Every body also
carries an explicit \texttt{kind} field, with value \texttt{session},
\texttt{delegation}, or \texttt{invocation}, inside its signed encoding.
The verifier \emph{rejects} chains where the position-derived tag does
not match a body's \texttt{kind} --- preventing chain-extension attacks
that would attempt to reuse an invocation token as a delegation, or vice
versa. Such a body would fail the aggregate check in any case, since the
verifier would hash it under a tag it was not signed with. The explicit
field lets the verifier reject it in phase 1, before any pairing, and
removes any ambiguity about how a body is to be parsed.

\subsection{Parameter Binding}
\label{sec:protocol-params}

Parameter binding is achieved by including the canonical encoding of
parameter values directly in the message $m_N$ that the invoking agent
signs. Any modification to parameter values --- changing an amount,
substituting a recipient, altering a file path --- changes the
canonical encoding, which changes $m_N$, which invalidates the
signature contribution $\sigma_N$ to the aggregate.

To support nested parameter structures (e.g.,
\texttt{order.payment.amount}), parameter values are encoded as a
nested CBOR map with text-string keys sorted lexicographically by
encoded form (per RFC 8949 §4.2.1). Parameter values are restricted to
unsigned and signed integers, byte strings, NFC-normalized text
strings, booleans, null, and nested maps and arrays of the same. Float
values and tagged values are disallowed in parameter encodings, to
eliminate edge cases around floating-point comparison and the
introduction of unexpected types. Parameter map \emph{keys} are
text strings and are NFC-normalized on the same terms as text values.
Without an explicit rule for keys, two implementations could
canonically re-encode the same logical parameter map to different byte
strings, and the re-encoding check of \cref{sec:protocol-encoding}
would diverge between them.

Parameter binding is a cryptographic property, not an authorization
one. It guarantees that the values a verifier reads are the values the
invoking agent signed; it says nothing about whether those values were
permitted. Whether they were is decided by the policy evaluation of
\cref{sec:policy-eval}, whose closed-world treatment of undeclared
parameters is what turns binding into constraint.

The InvocationBody also includes \texttt{params\_hash}, a SHA-256
digest of the canonical parameter encoding. The verifier recomputes
this hash from the encoded parameters and rejects any chain where it
does not match. This is redundant with the signature check but serves
as defense-in-depth against subtle encoding bugs in implementations.

\subsection{Approval Receipts}
\label{sec:protocol-approvals}

When policy requires human approval for an action, the InvocationBody
carries an \emph{approval receipt} signed by a registered approval
service. The receipt binds the human's approval decision to the
specific invocation being approved.

The flow is as follows. The agent constructs the InvocationBody
\emph{except} for the approval receipt field, computes a digest over
this preliminary body, and submits the digest along with the full body
to the required approval service. The service presents the proposed
invocation to a human approver. On approval, the service signs an
\emph{approval body} containing the service's identifier and public
key, the invocation digest, opaque attestation data identifying the
approver, and timing fields. The signed receipt is returned to the
agent, which embeds it in the now-complete InvocationBody and proceeds
with chain construction.

The approval signature is verified separately from the main aggregate.
This decoupling has two consequences. First, the security argument for
chain integrity does not depend on approval service trust:
compromise of an approval service does not enable chain forgery.
Second, approval verification adds a single pairing operation per
approval (typically zero or one per invocation), which we judge an
acceptable cost.

Policy can require approvals from multiple services (logical AND); the
required service identifiers and public keys are part of the policy
that the session token's \texttt{policy\_hash} commits to. The policy
hash is fixed at session start and does not vary with where the agent
sends its approval request, so an agent that routes to a different
(perhaps more permissive) service still presents the correct hash. What
it cannot present is a receipt from a service the policy requires. The
verifier, having resolved the policy that the hash commits to, and
having checked that every scope in the chain is contained in it
(\cref{sec:policy}), obtains an approval requirement no weaker than the
policy's own, and rejects a chain whose receipts do not cover it. This
is the defense against the approval routing attack (\threatref{4b}).

\subsection{Verification}
\label{sec:protocol-verification}

The verifier algorithm proceeds in phases, ordered to fail fast on
cheap checks before performing expensive cryptographic operations.
\Cref{alg:verify,alg:verify2} state the procedure; the paragraphs that
follow comment on individual phases. Every \textbf{reject} is terminal, and no
state is mutated before the final step, so a chain that fails any check
leaves the verifier exactly as it found it.

Three abbreviations keep the statement short, all of them reading fields
named in \cref{sec:protocol-digest}. Write $\mathrm{sid}(B_k)$ for the
identifier of the party that signed $B_k$: \texttt{issuer\_id} for the
session body, \texttt{delegator\_id} for a delegation body,
\texttt{invoker\_id} for the invocation body. Write $\mathrm{spk}(B_k)$
for that party's public key as named in the body --- \texttt{delegator\_pk}
or \texttt{invoker\_pk}; the session body names its subject's key, not
its issuer's, so $\mathrm{spk}(B_0)$ is undefined and $\pk_0$ comes from
the resolved certificate alone. Write $\mathrm{scope}(B_k)$ for the
body's scope expression: the granted scope for the session body, the
attenuated sub-scope for a delegation body. Finally, $\mathrm{org}(x)$ is
the \texttt{organization-id} prefix of an identifier $x$
(\cref{sec:identity-registration}); $\mathit{Root}[o]$ is the registry
root key the verifier holds for organization $o$
(\cref{sec:identity-federated}); and $\mathit{Pinned}[o]$ is the set
of policy hashes the verifier has accepted from organization $o$
(\cref{sec:policy}).

\paragraph{Structural and temporal checks.}
The verifier first decodes the received chain and confirms canonical
encoding (rejecting non-canonical inputs to prevent encoding-ambiguity
attacks). It then checks that the current time is within the
invocation's validity window, that expiry times are monotonically
non-increasing along the chain (each hop's expiry cannot exceed its
parent's), and that the chain has minimum length one.

\paragraph{Replay protection.}
The verifier maintains a bounded-time nonce cache indexed by
$(\text{invoker public key}, \text{nonce})$. Chains whose key is
already present in the cache are rejected as replays. Successful
verifications add the key to the cache with TTL equal to the chain's
remaining validity window plus a clock-skew tolerance. The cache size
is bounded by the product of maximum verification throughput and the
maximum validity window.

The cache must be a single logical structure. A deployment that places
several verifier replicas behind a load balancer, each holding its own
independent cache, does not provide replay protection at all: the same
chain presented to two replicas is accepted twice, and an adversary who
can influence load-balancer routing can replay at will. Replicated
verifiers must therefore share a cache or partition it deterministically
by invoker public key. This is a coordination dependency on the
verification path, and \cref{thm:replay} is stated with it as an
explicit hypothesis.

\paragraph{Public key chain consistency.}
The verifier checks that each body is signed by the party its
predecessor named. The session body's subject key must equal the signer
key of $B_1$, and each delegation body's delegatee key must equal the
signer key of the body that follows it. The signer key of a delegation
body is its delegator key, and that of the invocation body is its
invoker key, so the rule also covers the shortest chain: when $N = 1$
there are no delegations, and the orchestrator named in the session is
itself the invoker.

\paragraph{Scope monotonicity and policy compliance.}
The verifier first confirms that the session token's
\texttt{policy\_hash} is one it has pinned for the issuing organization
(\cref{sec:policy}). It then obtains the policy document, from its cache
or by hash from the issuing registry (\cref{sec:identity-resolution}),
and establishes the containment chain \cref{eq:chain-containment} using
the procedure of \cref{sec:policy-subset}: the session scope must lie
within the policy, and each hop's sub-scope within its parent's. Finally
it evaluates the invocation against the innermost scope, rejecting if
the invocation falls outside it. The pinning check is what gives the
first link its force. The issuer signs both the policy hash and the
session scope, so without pinning the verifier would be checking the
issuer against a policy the issuer had selected.

\paragraph{Approval verification.}
If policy requires approvals, the verifier confirms that all required
approval services have signed valid receipts binding to the correct
invocation digest, and rejects the chain otherwise.

\paragraph{Aggregate signature verification.}
Finally, the verifier reconstructs $m_0, m_1, \ldots, m_N$ from the
received bodies (using position-determined tags) and checks the
aggregate via a multi-pairing:
\begin{equation}
\pair{g_1}{\sigma_{\text{agg}}} \overset{?}{=}
    \prod_{k=0}^{N} \pair{\pk_k}{\HashG(m_k)}.
\end{equation}
If this check succeeds, all integrity, parameter-binding, and chain
provenance properties hold simultaneously.

\paragraph{Cost.}
The aggregate check has a single multi-pairing structure with $N+2$
internal pairings. In modern BLS libraries (e.g., \texttt{blst}), the
Miller loops of these pairings share computation, and only a single
final exponentiation is required. The empirical cost is well
approximated by $\alpha + \beta N$ where $\alpha$ is the dominant final
exponentiation cost and $\beta$ is the per-Miller-loop cost. For chain
lengths $N \le 10$ (which we expect to cover the overwhelming majority
of practical deployments), the variation with $N$ is small relative
to $\alpha$, and total verification latency is dominated by the constant
term. This is significantly more favorable than verification approaches
requiring network round-trips per hop (e.g., OAuth token
introspection), but does not amount to truly asymptotic $O(1)$
verification; the honest characterization is ``compact aggregate
signatures with multi-pairing efficiency.''

\Cref{fig:phases} shows why the order matters. The phases are arranged
so that the checks a hostile chain is most likely to fail are also the
cheapest to run: a malformed or expired chain is rejected on parsing and
integer comparison, and only a chain that has survived every structural,
temporal, and policy check reaches the pairing computation. An adversary
who wishes to make a verifier do the expensive work must first construct
a chain that is well-formed, unexpired, non-replayed, key-consistent,
scope-monotone, and policy-compliant --- at which point the aggregate
check is the only thing left to establish, and the work is warranted.

\subsection{Encoding}
\label{sec:protocol-encoding}

All signed structures use deterministic CBOR encoding per RFC 8949
§4.2.1, with the following additional rules. In \emph{protocol
structures} --- session, delegation and invocation bodies,
certificates, and approval receipts --- map keys are integers rather
than text strings, eliminating UTF-8 normalization considerations and
reducing encoding size. Parameter maps are the exception: they carry
names chosen by the tool author rather than by this specification, and
so use text-string keys sorted lexicographically by encoded form, per
\cref{sec:protocol-params}. The scoping is deliberate, and an
implementation that applies the integer-key rule to parameter maps will
not interoperate with one that does not. Float and tagged values are
disallowed in protocol structures except where explicitly required.
Group elements are encoded using the standard ZCash-format compressed
serialization defined for BLS12-381, and decoders perform subgroup
membership checks on every group element to defend against
small-subgroup attacks.

Verifiers reject any structure whose received encoding differs from
the canonical re-encoding of the decoded content. This precludes a
class of attacks based on adversarially-crafted non-canonical encodings
that parse correctly but hash to different values than the
implementation expects.

\section{Identity Infrastructure}
\label{sec:identity}

The cryptographic protocol of \cref{sec:protocol} assumes that
verifiers can resolve identity-to-public-key bindings for all
participants in a chain. This section describes the federated identity
infrastructure providing those bindings, including registration with
proof-of-possession, public-key resolution, key rotation, and
revocation.

\subsection{Federated Registry Model}
\label{sec:identity-federated}

DelegationChain does not assume a global root of trust. Each
participating organization operates its own \emph{registry}, which
issues identity certificates for agents, signing services, and
approval services within that organization. Each registry holds a
long-lived root keypair, with the root public key serving as the trust
anchor for all certificates the registry issues.

Two organizations establish trust through one of three mechanisms,
chosen per deployment. \emph{Direct peering} exchanges registry root
keys out-of-band as part of a business agreement; this is the simplest
model and adequate for small numbers of partners. \emph{Federated
transparency} publishes registry root keys and certificate issuances
to a shared append-only log, modeled on Certificate Transparency
\citep{rfc9162} but adapted to DelegationChain's certificate format;
verifiers trust the log's commitments and obtain inclusion proofs
binding claimed keys to log entries. \emph{Hierarchical attestation}
introduces an attestation authority signing statements binding
registry roots to organizational identifiers, analogous to a root
CA. The protocol permits all three; we recommend direct peering or
federated transparency over hierarchical attestation, the latter
inheriting the trust-concentration concerns of Web PKI.

These mechanisms are not mutually exclusive. A production deployment
may use direct peering with frequent partners and a federated log for
the long tail. Whatever the mechanism, the peering relationship is also
where the receiving organization fixes which of its partner's policies
it will honor. Its verifiers pin those policy hashes and reject
sessions naming any other (\cref{sec:policy}).

\subsection{Identifiers and Registration}
\label{sec:identity-registration}

Identifiers are structured as
\texttt{organization-id:kind:local-id}, where \texttt{kind} is one of
\texttt{agent}, \texttt{signer}, or \texttt{approver}. The
\texttt{kind} tag prevents identifier confusion across roles. The
\texttt{organization-id} matches the issuing registry's identifier.

Registration produces a certificate binding an identifier to a public
key, signed by the registry. Certificates contain version
information, the identifier, the public key, the kind, the registry's
identifier (\texttt{registry\_id}) and public key, issuance and expiry
timestamps, a
not-before timestamp, a serial number, and the registry's signature.
Default certificate lifetimes are short --- 24 hours to 7 days for
agents and signing services, with longer lifetimes permitted only in
combination with active revocation (\cref{sec:identity-revocation}).
Short lifetimes reduce reliance on revocation by ensuring that
compromised credentials naturally expire within a bounded window.

\subsection{Proof of Possession}
\label{sec:identity-pop}

BLS aggregate signatures are vulnerable to rogue-key attacks unless
registrants prove possession of the secret keys corresponding to
registered public keys \citep{boneh2018compact}. Without
proof-of-possession (PoP), an adversary could register a public key
$\pk^* = \pk' - \sum_i \pk_i$ for chosen targets $\pk_i$ and a key
$\pk'$ for which the adversary holds the secret; valid signatures
$\sigma_i$ from the targets could then be combined with an adversary
signature to forge an aggregate that includes $\pk^*$.

DelegationChain requires every registration to include a PoP signature
over a registry-issued challenge. The challenge includes the
registrant's claimed identifier and public key, the kind tag, the
registry's identifier, a registry-issued fresh nonce (single-use,
short expiry), and a timestamp. The registrant computes a BLS
signature over this challenge with the secret key corresponding to the
public key being registered. The registry verifies the PoP signature
before issuing the certificate. The registry-issued nonce prevents
replay of PoPs captured from other contexts.

Registries additionally perform subgroup membership checks on
registered public keys, rejecting points that do not lie in the
prime-order subgroup of $\G{1}$. This check is non-trivial on BLS12-381
and has been the source of real-world implementation vulnerabilities.
Implementations should use library-provided subgroup checks (e.g.,
\texttt{blst\_p1\_in\_g1}) rather than reimplementing them.

\subsection{Public Key Resolution}
\label{sec:identity-resolution}

Verifiers resolve identifiers to public keys by querying the issuing
registry's resolution endpoint. The response includes the certificate
and, if the registry is integrated with a transparency log, an
inclusion proof. The verifier validates the certificate signature under
the root public key it holds for the organization the identifier names,
that is, for the identifier's \texttt{organization-id} prefix, bound to
a root key by whichever trust mechanism of \cref{sec:identity-federated}
the two organizations use. It also requires the certificate's
\texttt{registry\_id} to equal that \texttt{organization-id}. If an
inclusion proof is present, the verifier checks it against the log's
current signed tree head.

This binding between organization identifier and root key carries real
weight. A registry is authoritative only for identifiers in its own
organization's namespace. The naming rule of
\cref{sec:identity-registration} is enforced here, by the verifier,
rather than left as a convention. Without it, a registry the verifier
trusts for one organization could issue a certificate for another
organization's identifier: a certificate substitution
(\threatref{5d}). And because the verifier looks up pinned policies by
the organization named in the session body (\cref{sec:policy}), whoever
controlled that registry could impersonate the other organization's
issuer and grant sessions under the policies pinned for it.

Verifiers cache resolved certificates to avoid registry queries on
every verification. Cache entries are valid until the earlier of the
certificate's expiry and a configurable cache TTL (typically one
hour). Cache invalidation is event-driven for revocation: observation
of a revocation assertion immediately evicts the corresponding cached
entry.

\paragraph{Policy resolution.}
The verifier must also hold the policy that a session token's
\texttt{policy\_hash} commits to; \cref{sec:protocol-verification} checks the
session scope against it using the containment relation of
\cref{sec:policy-subset}, \cref{sec:policy-eval} then evaluates the
invocation against the innermost scope, and
\cref{thm:approval-binding} depends on that policy being one the
verifier accepted, not one the chain selected. Since the policy is written by the sending
organization and enforced by the receiving one, it has to get across the
boundary somehow, and the protocol should not leave this unsaid.

Registries host policy documents alongside certificates, retrievable by
hash: a verifier holding \texttt{policy\_hash}~$h$ requests the document
$h$ names, and accepts it only if $H(\Canon(\text{document})) = h$.
Because resolution is content-addressed, the registry is not trusted
for integrity --- it cannot substitute a different policy, only decline
to serve one --- which is the same posture the rest of
\cref{sec:identity} takes towards registries. Policies are immutable
under their hash, so a document once fetched is cached for as long as
the verifier keeps it; a policy change produces a new hash and, hence, a
new session token rather than a silent change under an existing one.

Pinning (\cref{sec:policy}) keeps this fetch off the request path.
Because a verifier accepts only hashes it has pinned, it knows every
hash it will need before any chain names one, and it can fetch and check
the documents when it pins them. A hash it has not pinned is rejected
without any fetch. A verifier that defers fetching to first use pays one
round trip on that call; \cref{sec:limitations} discusses what the
remaining dependencies cost the offline-verification claim.

\subsection{Key Rotation}
\label{sec:identity-rotation}

The protocol supports three rotation modes. \emph{Scheduled rotation}
issues a new certificate with overlapping validity windows: during the
overlap, both old and new keys are valid, ensuring that chains in
flight at the moment of rotation continue to verify. Default rotation
cadence is every 30 days for agents and every 90 days for signing
services and approval services. \emph{Emergency rotation} truncates
the validity of the prior certificate via an immediately-issued
revocation assertion (\cref{sec:identity-revocation}) and issues a new
certificate without overlap. \emph{Registry root rotation} is the most
sensitive operation: the current root signs a rotation attestation
binding the new root to the old, which is then distributed via the
same channel used for the original root. Compromised-root recovery
requires out-of-band re-bootstrap of trust and cannot be handled by
in-band rotation.

Rotation interacts with chains that are in flight when a key changes.
Under scheduled rotation the overlapping validity windows cover this
case: a chain signed under the previous key continues to verify for the
duration of the overlap, because the previous certificate is still
valid. Under emergency rotation there is no overlap, and chains signed
under the withdrawn key are rejected. The verifier always resolves the
certificate valid at \emph{verification} time. It does not attempt to
resolve the certificate that was valid when a token was signed, because
its only evidence of signing time would be a field in the token body,
signed by the very key whose compromise is at issue;
\cref{sec:identity-revocation} develops this point.

\subsection{Revocation}
\label{sec:identity-revocation}

DelegationChain prefers short-lived certificates over revocation
infrastructure: with default certificate lifetimes of 24 hours to 7
days, the maximum window during which a compromised key can be misused
is bounded by certificate expiry. Explicit revocation is provided as a
defense-in-depth mechanism for deployments choosing longer-lived
certificates.

A \emph{revocation assertion} is a signed statement by a registry
declaring that a specific certificate is revoked, identified by serial
number. Verifiers learn of assertions through polling (default
interval 60 seconds), push notification, or transparency log
monitoring; the choice is a deployment decision. The end-to-end window
between key compromise and unforgeability is bounded by the sum of
detection latency, reporting latency, assertion issuance,
propagation, and residual cache time, of which only the propagation and
cache terms are bounded by configuration (typically below 120
seconds). Detection and reporting latency are unbounded by the
protocol: they depend on the deploying organization's monitoring, and
nothing in the design constrains them. The property claimed in
\cref{sec:threat-properties} is accordingly bounded revocation
\emph{propagation}, not bounded exposure.

Revocation applies relative to \emph{verification time}. A certificate
revoked at time $t_r$ is not accepted by any verifier that has learned
of the revocation, including for chains whose tokens were signed before
$t_r$. The gentler alternative --- continuing to honor chains signed
before $t_r$, so that revocation does not retroactively invalidate work
already in progress --- is not available to us. A verifier's only
evidence of signing time is a timestamp in the token body, and that
timestamp is signed by the key whose compromise prompted the
revocation. An adversary holding a stolen key, observing the
revocation, can set the field to any earlier value and produce a chain
that verifies against the pre-revocation certificate. A revocation rule
resting on that field can be defeated by backdating, which would leave
the mechanism without force.

We therefore accept the operational cost. Chains in flight when a
revocation is issued may fail verification and must be reconstructed
under a rotated key. Two things bound the exposure: only chains
outstanding within the propagation window are affected, and scheduled
rotation (\cref{sec:identity-rotation}) avoids the situation entirely by
overlapping the validity windows of the old and new certificates, so
that routine key changes never invalidate work in flight. Emergency
rotation, by construction, does.

\section{Policy Expression Language}
\label{sec:policy}

This section introduces the policy expression language used to describe
agent authorization scopes throughout DelegationChain. The language
serves two roles, and separating them is worth doing at the outset,
because the verifier treats them differently.

A \emph{policy} is a scope expression published by an organization for
its agents and committed to by the \texttt{policy\_hash} field of the
session token (\cref{sec:protocol-digest}). It is a ceiling: the outer
bound on what any agent operating under that session may do, fixed by
the organizations involved rather than by any agent. The session names
which policy applies; the verifier decides which policies it will
accept at all, as described below, and resolves the document from the
registry by hash (\cref{sec:identity-resolution}). A \emph{scope} is a scope expression
carried inside a token --- the authority the issuer granted the
orchestrator, in the session token, and the attenuated sub-scope each
delegator passed on, in a delegation token.

Both are drawn from the same grammar, and a single relation connects
them. A chain is accepted only if
\begin{equation}
\label{eq:chain-containment}
S \supseteq \mathrm{scope}(B_0) \supseteq \mathrm{scope}(B_1)
  \supseteq \cdots \supseteq \mathrm{scope}(B_{N-1}),
\end{equation}
where $S$ is the resolved policy and $B_0, \ldots, B_{N-1}$ are the
session and delegation bodies. Every link is checked by the containment
procedure of \cref{sec:policy-subset}; the verifier then evaluates the
invocation against $\mathrm{scope}(B_{N-1})$, the innermost scope.

The first link needs care, because the issuer signs both
\texttt{policy\_hash} and $\mathrm{scope}(B_0)$ in the same body. If the
verifier accepted whatever hash a session named, the check would compare
the issuer against a policy the issuer had chosen. Content addressing
prevents a different document from being substituted behind a hash, but
it does nothing about which hash is selected. The verifier therefore
accepts only policies it has \emph{pinned} for the issuing organization:
a set of policy hashes fixed in its own configuration, or in the peering
agreement with that partner (\cref{sec:identity-federated}). A session
naming any other hash is rejected. The ceiling $S$ is then drawn from a
set the receiving organization agreed to, and the issuer can do no more
than choose among policies the verifier has already accepted.

Pinning also closes a gap the protocol would otherwise leave: the
receiving organization had no way to state its own terms, only to
enforce the sending organization's. A pinned policy may be one the
sending organization published and the receiving organization reviewed,
or one the two wrote together for the relationship. Either way, it is
never one the receiving organization has not seen. What pinning does not
defend against is the verifier's own configuration. We treat the pinned
set as part of the verifier's trust base (\cref{sec:security-assumptions}).

With pinning in place, every link of \cref{eq:chain-containment} belongs
to the scope monotonicity property of \cref{sec:threat-properties}, and
\cref{thm:scope-monotonicity} states it for the whole chain.

One consequence carries the weight of \cref{thm:approval-binding}.
\Cref{def:subset} requires a contained scope's approval requirement to
be at least as restrictive as its container's, so approval requirements
can only strengthen as one moves right along
\cref{eq:chain-containment}. An approval requirement written into the
policy therefore cannot be weakened by the issuer, nor by any agent
further down the chain. This is what lets the verifier evaluate against
$\mathrm{scope}(B_{N-1})$ --- data the agents wrote --- and still be
certain the requirement it obtains is no weaker than the one in a
policy it has itself accepted.

The design of the policy language is constrained by three requirements
arising from its role in the protocol. First, the verifier must be able
to check cheaply, given two scope expressions $S_1$ and $S_2$
purportedly in a delegation relationship, whether $S_2 \subseteq S_1$ ---
the scope monotonicity check of \cref{sec:protocol-verification} ---
erring towards rejection where it cannot establish containment. Second,
evaluation of an invocation against a scope must terminate in time
bounded by the size of the scope expression and the invocation, with
no possibility of unbounded computation. Third, scope expressions must
be free of side effects: evaluation must not perform network calls,
file I/O, or other operations that could be exploited for information
exfiltration or denial of service.

These requirements rule out general-purpose policy languages such as
Rego or Cedar, which are powerful but operationally expensive to reason
about and historically have included features (e.g., HTTP fetches in
some versions of Rego) that violate the side-effect-free requirement.
DelegationChain's policy language is deliberately restricted to a
fragment that supports realistic enterprise authorization conditions
while admitting straightforward decidability and termination analyses.

\subsection{Grammar}
\label{sec:policy-grammar}

The grammar of scope expressions, in Backus-Naur form:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
scope    ::= rule+ | "allow" "all" | "deny" "all"
rule     ::= "allow" tool action params? where? approval?
tool     ::= "tool" "=" identifier
action   ::= "action" "=" identifier
params   ::= "params" "{" binding ("," binding)* "}"
binding  ::= path ":" type
where    ::= "where" expr
expr     ::= expr "and" expr
           | "(" expr ")"
           | atom
atom     ::= path numop value
           | path strop string-value
           | path "in" list-value
           | path "under" path-value
type     ::= "int" | "string" | "bool" | "path"
numop    ::= "<" | "<=" | "==" | ">=" | ">"
strop    ::= "==" | "starts_with" | "ends_with" | "contains"
path     ::= identifier ("." identifier)*
value    ::= integer | string | boolean
list-value ::= "[" value ("," value)* "]"
\end{lstlisting}

A scope is either a special form (\texttt{allow all}, \texttt{deny all})
or a non-empty disjunction of \emph{rules}. Each rule specifies a tool,
an action, an optional declaration of expected parameter types
(\texttt{params}), an optional condition on parameter values
(\texttt{where}), and an optional approval requirement
(\texttt{approval}). The semantics of a scope is the union of the
invocations permitted by its rules; \texttt{deny all} permits nothing,
and \texttt{allow all} is a reserved form used for top-level trusted
contexts (e.g., the issuer's session-issuance authority).

The condition language inside \texttt{where} clauses is
\emph{conjunctive}: a clause is a conjunction of atomic predicates over
parameter values. Each atomic predicate is one of four forms --- numeric
comparison, string operator, list membership (\texttt{in}), or
path-prefix containment (\texttt{under}). No predicate involves function
calls, network operations, or unbounded iteration.

Disjunction and negation are deliberately absent from the expression
language. Disjunction is recovered one level up: a scope is a union of
rules, so a condition $a \lor b$ is written as two rules, and the
expressive loss is close to nil. Negation is recovered only in part.
Numeric comparisons have complements within the language --- the
negation of $x > c$ is $x \le c$ --- but the string, membership, and
path-prefix predicates do not, so a condition such as ``the path is
\emph{not} under \texttt{/etc}'' cannot be written. We accept this.
Authorization policies are more naturally written as enumerations of
what is permitted than as exclusions of what is not, and the restriction
is what buys the containment procedure of \cref{sec:policy-subset} its
polynomial running time: implication between arbitrary propositional
formulas is coNP-complete, and a verifier is not a good place to run a
SAT solver on an input the sender chose.

\subsection{Example}
\label{sec:policy-example}

A representative policy fragment governing a payments tool:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
allow tool=payments action=transfer
  params { amount: int,
           to_account: string }
  where amount <= 1000
allow tool=payments action=transfer
  params { amount: int,
           to_account: string }
  where amount <= 100000
        and to_account in
            ["acct_vendor_a", "acct_vendor_b"]
  approval requires approval_service_finance
allow tool=files action=read
  params { path: path }
  where path under "/home/agent/workspace"
\end{lstlisting}

This policy permits unconditional transfers up to 1{,}000 units;
transfers up to 100{,}000 units to two approved vendors with finance
approval; and read access to files anywhere under a specific workspace
directory. Any invocation falling outside these three rules is denied
by the implicit closing rule \texttt{deny all}.

\subsection{Evaluation Semantics}
\label{sec:policy-eval}

Given a scope $S$ and an invocation
$I = (\text{tool}, \text{action}, \text{params})$, the evaluator returns
\textsc{allow}, \textsc{allow-with-approval}(\textit{services}), or
\textsc{deny}. The procedure is:

\begin{enumerate}
    \item For each rule $r$ in $S$ in declaration order:
    \begin{enumerate}
        \item If $r$'s tool and action do not match $I$, continue.
        \item Type-check $I.\text{params}$ against $r$'s
              \texttt{params} declaration. The check is
              \emph{closed-world}: the rule matches only if
              $\mathrm{dom}(I.\text{params})$ is exactly the set of
              parameter paths $r$ declares, and every value has its
              declared type. If a declared parameter is missing, if any
              parameter has the wrong type, or if the invocation carries
              a parameter $r$ does not declare, continue.
        \item Resolve each path mentioned in $r$'s \texttt{where}
              clause against $I.\text{params}$. If any path resolves
              to absent, continue (treating the rule as inapplicable).
        \item Evaluate $r$'s \texttt{where} clause. If false, continue.
        \item If $r$ has no approval requirement, return \textsc{allow}.
              Otherwise return \textsc{allow-with-approval}($r$'s
              required approval services).
    \end{enumerate}
    \item If no rule matched, return \textsc{deny}.
\end{enumerate}

\paragraph{The closed-world condition.}
Step 1(b) is closed-world by design: an invocation carrying a parameter
that the rule does not declare matches no rule, and is denied. The
alternative --- checking declared parameters and ignoring the rest ---
would leave undeclared parameters cryptographically bound but never
authorized. Under \cref{sec:protocol-params} every supplied value sits
inside $\Canon(P)$ and is therefore signed and non-repudiable, but
binding is not constraint. A rule declaring \texttt{amount} and
\texttt{to\_account} says nothing about a third parameter
\texttt{override\_limits}, and a verifier that accepted an invocation
carrying it would be honoring an authorization the policy never
granted. Closing the world is what makes a parameter declaration a
constraint rather than a schema hint.

\paragraph{Match order.}
Rules are tried in declaration order and the first match wins, so a
broad early rule silently suppresses the approval requirement of a
narrower rule later in the scope. In the policy of
\cref{sec:policy-example} a 500-unit transfer to
\texttt{acct\_vendor\_a} matches rule 1 and returns \textsc{allow}
without ever reaching rule 2's finance approval. This is a
policy-authoring hazard rather than a protocol defect --- the outcome is
exactly what the written policy says --- but it is easy to introduce by
accident, and authors should order rules from most restrictive to least,
or scope early rules narrowly enough that they cannot shadow a later
approval requirement.

The evaluator is deterministic, has no side effects, and contains no
loops over data of unbounded size: the outer loop iterates over rules
(a finite syntactic component of $S$), and \texttt{where} clause
evaluation is a finite recursive descent over the expression tree.

\begin{proposition}[Termination]
\label{prop:termination}
Evaluation of an invocation against a scope $S$ terminates in time
$O(|S| \cdot |\text{params}|)$, where $|S|$ is the syntactic size of the
scope expression and $|\text{params}|$ is the total size of the
invocation's parameter encoding.
\end{proposition}

\begin{proof}[Proof sketch]
The outer loop iterates over rules of $S$, of which there are at most
$|S|$. For each rule, parameter resolution traverses the parameter map,
which is bounded by $|\text{params}|$; \texttt{where} expression
evaluation is a recursive descent whose depth is bounded by the
syntactic depth of the expression, itself bounded by $|S|$. The total
work is bounded by the product, yielding the claimed bound.
\end{proof}

\subsection{Subset Relation}
\label{sec:policy-subset}

The verifier of \cref{sec:protocol-verification} must check that the
sub-scope at each delegation hop is a subset of its parent's scope.
This is a check over scope expressions, performed once per hop at
verification time, and not a runtime check over invocations. We define
the relation semantically and then give a syntactic procedure that
soundly under-approximates it.

\begin{definition}[Subset relation]
\label{def:subset}
Given scope expressions $S_1, S_2$, we say $S_2 \subseteq S_1$ iff every
invocation $I$ that the evaluator accepts under $S_2$ is also accepted
under $S_1$, with at least as restrictive an approval requirement.
\end{definition}

Containment is checked --- conservatively, as \cref{prop:decidability}
and \cref{rem:incompleteness} make precise --- by the following
procedure:

\begin{enumerate}
    \item If $S_1$ is \texttt{allow all}, return true.
    \item If $S_2$ is \texttt{deny all} or has no rules, return true.
    \item For each rule $r_2$ in $S_2$:
    \begin{enumerate}
        \item Attempt to find a rule $r_1$ in $S_1$ such that
              $r_2 \subseteq r_1$ as rules. If no such $r_1$ exists,
              return false.
        \item For every rule $r'$ of $S_1$ that agrees with $r_2$ on
              tool, action, and parameter declaration and whose
              \texttt{where} clause is jointly satisfiable with $r_2$'s,
              check that $r'$'s approval requirement is no stronger
              than $r_2$'s. If some $r'$ fails this check, return false.
    \end{enumerate}
    \item Otherwise, return true.
\end{enumerate}

Step 3(b) is needed because rules are matched in declaration order
(\cref{sec:policy-eval}). An invocation accepted under $S_2$ is
evaluated under $S_1$ against the \emph{first} rule of $S_1$ that
matches it, which need not be the subsuming rule $r_1$ that step 3(a)
found. Without the additional check a child scope could quietly drop an
approval requirement imposed by an earlier parent rule --- exactly the
escalation \cref{def:subset} is meant to exclude --- and the procedure
would not notice. Checking all candidate rules rather than only those
preceding $r_1$ is conservative, which is the direction of error we
want.

Rule subsumption ($r_2 \subseteq r_1$) requires: the tools and actions
match; $r_1$ and $r_2$ declare the \emph{same} set of parameter paths
with the same types; $r_1$'s approval requirement is no stronger than
$r_2$'s (so that any approvals satisfying $r_2$ also satisfy $r_1$);
and $r_2$'s \texttt{where} clause implies $r_1$'s.

The identity condition on parameter declarations follows from the
closed-world rule of \cref{sec:policy-eval}. Because a rule matches only
invocations whose parameter set is exactly what it declares, two rules
declaring different parameter sets accept disjoint sets of invocations:
declaring fewer parameters is strictly more restrictive rather than more
permissive, and no containment holds in either direction. Requiring
identical declarations is therefore the only sound relation available
without further machinery, such as an explicit notion of optional
parameters that the language does not currently have.

The remaining sub-problem is deciding implication between \texttt{where}
clauses. Because a clause is a conjunction of atoms
(\cref{sec:policy-grammar}), this reduces to a check over atoms rather
than to satisfiability. The atoms have a restricted structure: numeric
comparisons are over a fixed integer path and constants, string
operators are over fixed string paths and constant patterns, list
membership is over fixed lists, and path-prefix containment is over
fixed prefixes. Atoms over distinct paths are independent, so a
conjunction $C_2 = \bigwedge_j a_j$ implies a conjunction
$C_1 = \bigwedge_i b_i$ exactly when, for each $b_i$, those atoms of
$C_2$ over the same path as $b_i$ jointly imply $b_i$. For each of the
four atom forms this is a closed-form check on the constraint the atoms
induce on that path: an interval for numeric comparisons, a set of
admissible values for membership, and a prefix or substring relation for
the string and path operators. Joint satisfiability, needed by step
3(b), is the same analysis: a conjunction is unsatisfiable exactly when
the constraints induced on some path are inconsistent. No search over
truth assignments is required at any point.

\begin{proposition}[Soundness and cost of the containment procedure]
\label{prop:decidability}
The procedure above terminates in time polynomial in $|S_1| + |S_2|$,
and whenever it returns true, $S_2 \subseteq S_1$ in the sense of
\cref{def:subset}.
\end{proposition}

\begin{proof}[Proof sketch]
\emph{Cost.} The procedure enumerates pairs
$(r_2, r_1) \in S_2 \times S_1$, of which there are at most
$|S_1| \cdot |S_2|$. Each pair check compares two identifiers, compares
two parameter declarations for equality, compares two approval
requirements, and decides implication between two conjunctions of
atoms. The last of these groups the atoms of each clause by path and,
for each atom of $r_1$'s clause, evaluates a closed-form implication
against the constraint that $r_2$'s atoms induce on the same path; the
number of such checks is bounded by the product of the two atom counts,
and each is constant-time in the atom's operands. Step 3(b) performs a
satisfiability check of the same form over the same pairs. The total is
polynomial in $|S_1| + |S_2|$.

\emph{Soundness.} Suppose the procedure returns true, and let $I$ be an
invocation the evaluator accepts under $S_2$. Acceptance means some rule
$r_2 \in S_2$ matched $I$. Step 3(a) exhibited an $r_1 \in S_1$ with
$r_2 \subseteq r_1$. Then $r_1$ matches $I$ as well: the tool and action
agree, so step 1(a) of \cref{sec:policy-eval} passes; the parameter
declarations are identical, so the closed-world check of step 1(b)
passes; every path $r_1$'s clause mentions is declared and therefore
present, so step 1(c) passes; and $r_2$'s clause holds of $I$ and
implies $r_1$'s, so step 1(d) passes. Hence $I$ is accepted under $S_1$.
For the approval component, the rule that actually decides $I$ under
$S_1$ is the first rule of $S_1$ matching $I$; any such rule agrees with
$r_2$ on tool, action, and parameter declaration, and its clause is
satisfied by $I$ jointly with $r_2$'s, so it was examined by step 3(b)
and its approval requirement is no stronger than $r_2$'s. Thus $I$ is
accepted under $S_1$ with an approval requirement no stronger than the
one $S_2$ imposes, which is \cref{def:subset}.
\end{proof}

\begin{remark}[Incompleteness]
\label{rem:incompleteness}
The procedure is sound but not complete. Step 3(a) requires each rule of
$S_2$ to be subsumed by a \emph{single} rule of $S_1$, so a child rule
covered only by the union of several parent rules is rejected. Take
$S_1$ to be the two rules
\texttt{allow tool=t action=a params \{x: int\} where x <= 10} and
\texttt{allow tool=t action=a params \{x: int\} where x > 10}, and $S_2$
the single rule \texttt{allow tool=t action=a params \{x: int\}}. Every
invocation accepted under $S_2$ is accepted under $S_1$, so
$S_2 \subseteq S_1$ holds semantically; but neither rule of $S_1$
subsumes $S_2$'s rule on its own, and the procedure returns false. The
incompleteness is conservative --- the procedure rejects some legitimate
delegations and accepts no illegitimate ones --- and we prefer that
direction of error. Deciding \cref{def:subset} exactly would require
reasoning about unions of rules, which the per-rule structure of the
procedure does not support; we leave it open whether the exact relation
admits an efficient decision procedure for this language.
\end{remark}

\subsection{Limitations of the Policy Language}
\label{sec:policy-limitations}

The policy language is deliberately bounded. It cannot express
semantic conditions of the form ``is this email message
professional?'' or ``is this code review constructive?'' that would
require external evaluation, typically by another LLM. Such conditions
are non-deterministic and admit no obvious decidability or termination
guarantee, and we judge them inappropriate for inclusion in
authorization policies that must be cryptographically committed to via
\texttt{policy\_hash}.

The language also cannot express conditions referring to state outside
the invocation itself: account balances, current time relative to
business hours, counts of prior invocations within a window. Such
conditions either require stateful evaluation (which would violate the
side-effect-free requirement) or external queries (which would
introduce latency and additional trust dependencies). Where stateful
authorization is required, we anticipate it being handled at the tool
implementation layer, after the protocol's stateless authorization
check has succeeded.

The closed-world condition of \cref{sec:policy-eval} carries an
operational cost of its own. Adding an optional parameter to a tool is
not a backward-compatible change: every rule governing that tool must be
updated to declare the new parameter before any invocation may supply
it, and until the updated policy has propagated, invocations carrying
the new parameter are denied. Because policies are committed to by hash
in session tokens, that update is a policy version change rather than an
edit in place, and every partner whose verifiers accept the policy
must pin the new hash before sessions under it will verify. We consider this the right default, since the
failure mode is denial rather than unauthorized acceptance, but
deployments whose tool schemas change often should expect policy churn
in proportion.

These limitations are deliberate. A more expressive language would
provide more flexibility but at the cost of guarantees we consider
essential. We discuss possible extensions to semantic conditions via
verifiable LLM attestation in \cref{sec:discussion}.

\section{Security Analysis}
\label{sec:security}

This section presents the security argument for DelegationChain. We
state the protocol's security properties as theorems, reduce each to
standard cryptographic assumptions or to the properties of the policy
language, and sketch proofs. The arguments here are informal in the
sense that they have not been mechanized in a proof assistant or
verified using symbolic protocol analyzers such as Tamarin or
ProVerif. We discuss the planned formalization in
\cref{sec:limitations}.

\subsection{Assumptions}
\label{sec:security-assumptions}

The security arguments below rest on the following assumptions:

\begin{description}
    \item[\textbf{BLS unforgeability.}] The BLS signature scheme
    \citep{boneh2001bls,ietf-bls-signature}, instantiated on BLS12-381
    \citep{ietf-pairing-curves}, is
    existentially unforgeable under chosen-message attack, under the
    co-computational Diffie-Hellman assumption on the curve and in the
    random oracle model for $\HashG$.
    \item[\textbf{BLS aggregate security.}] Given proof-of-possession
    on all registered public keys, aggregate signatures are
    existentially unforgeable: no PPT adversary can produce a tuple
    $(\pk_1, \ldots, \pk_n, m_1, \ldots, m_n, \sigma_{\text{agg}})$
    with the $m_i$ pairwise distinct --- which
    \cref{sec:protocol-digest} guarantees, and which places no
    requirement on the $\pk_i$ being distinct --- such that the
    multi-pairing check accepts, unless the adversary has obtained
    valid individual signatures on each $m_i$ from the holder of
    $\sk_i$ \citep{boneh2018compact}.
    \item[\textbf{Collision resistance of SHA-256.}] SHA-256 is
    collision-resistant in the standard sense.
    \item[\textbf{Honest signing key custody.}] Signing keys remain in
    their designated hardware security modules and are not exfiltrated.
    Compromise of an HSM is explicitly out of scope per
    \cref{sec:threat-outside}.
    \item[\textbf{Honest registry root.}] Registry root signing keys
    are honestly managed. Compromise of a root is addressed via
    rotation and detection (\cref{sec:identity-rotation}); the
    formal arguments below assume an honest root, with the implication
    that root compromise reduces security to a recovery problem rather
    than a forgery problem.
    \item[\textbf{Verifier configuration integrity.}] The set of policy
    hashes a verifier has pinned for each partner, and the root key it
    associates with each partner organization, reflect its own
    organization's decisions and cannot be written by the adversary.
    The first link of \cref{eq:chain-containment}, and through it
    \cref{thm:scope-monotonicity,thm:approval-binding}, is only as good
    as that configuration.
\end{description}

\subsection{Theorems}
\label{sec:security-theorems}

\begin{theorem}[Token unforgeability]
\label{thm:unforgeability}
Under BLS unforgeability, no PPT adversary can produce a session,
delegation, or invocation token that verifies under a public key
$\pk$ for which it does not hold the corresponding $\sk$, except with
negligible probability.
\end{theorem}

\begin{proof}[Proof sketch]
A valid token consists of a body and a BLS signature on the body's
domain-tagged hash. Forging the signature without $\sk$ contradicts
BLS unforgeability under chosen-message attack: any adversary that
forges a token can be used to construct an adversary against BLS
unforgeability by treating the domain-tagged hash as the message and
extracting the signature.
\end{proof}

\begin{theorem}[Parameter binding]
\label{thm:parameter-binding}
A valid invocation token for parameters $P$ cannot be repurposed as
a valid invocation token for parameters $P' \neq P$, except with
negligible probability.
\end{theorem}

\begin{proof}[Proof sketch]
The signed message $m_N$ contains $\Canon(\text{InvocationBody})$,
which includes $\Canon(P)$. Under collision resistance of SHA-256 and
deterministic encoding, $\Canon(P) \neq \Canon(P')$ implies $m_N \neq
m_N'$. The signature $\sigma_N$ valid on $m_N$ is invalid on $m_N'$
by BLS unforgeability. The redundant \texttt{params\_hash} field
provides defense-in-depth against canonical encoding bugs but is not
required for the theorem.
\end{proof}

\begin{theorem}[Chain integrity]
\label{thm:chain-integrity}
The aggregate signature over a delegation chain covers the entire
chain content: any modification, reordering, truncation, or extension
of the chain invalidates the aggregate, except with negligible
probability.
\end{theorem}

\begin{proof}[Proof sketch]
Modification of any body changes its canonical encoding, changing the
corresponding $m_k$ (since $m_k$ hashes the body). Reordering changes
the sequence of $m_k$ values (since $m_k$ commits to $m_{k-1}$).
Truncation is caught by the same recursion. Suppose the adversary drops
$B_k$ for some interior $0 < k < N$. The verifier recomputes the
remaining messages from the bodies it actually receives, so where
$A_{k+1}$ signed
$m_{k+1} = H(\text{TAG\_DEL} \,\|\, m_k \,\|\, \Canon(B_{k+1}))$ the
verifier computes
$m'_{k+1} = H(\text{TAG\_DEL} \,\|\, m_{k-1} \,\|\, \Canon(B_{k+1}))$.
Since $m_k \neq m_{k-1}$ except with negligible probability under
collision resistance, $m'_{k+1} \neq m_{k+1}$, and every subsequent
message differs likewise. The adversary would need signatures under the
surviving hops' keys on messages those hops never signed, which
contradicts BLS aggregate security. Dropping the first or last hop is
caught earlier still, by the position-determined tag check: a chain
whose leading token is not a session token, or whose trailing token is
not an invocation token, is rejected in phase 1 of \cref{alg:verify}.
No assumption about the secrecy of individual $\sigma_k$ values is
required, and we make none --- the accumulation scheme of
\cref{sec:protocol-digest} would not support one.
Extension requires producing a new $\sigma$ for the extension hop;
under BLS aggregate security and proof-of-possession, this requires
the secret key of the extending party. The position-determined tag
check (\cref{sec:protocol-digest}) rejects chains where an invocation
token is repurposed as a delegation token (or vice versa) for chain
extension.
\end{proof}

\begin{theorem}[Scope monotonicity]
\label{thm:scope-monotonicity}
In any chain accepted by the verifier, every link of the containment
chain \cref{eq:chain-containment} holds in the sense of
\cref{def:subset}, where $S$ is a policy the verifier has pinned for the
issuing organization. In particular, the session scope is contained in
$S$, and the scope at hop $k+1$ is contained in the scope at hop $k$.
\end{theorem}

\begin{proof}[Proof sketch]
Phase 6 of \cref{alg:verify2} rejects any session whose policy hash is
not pinned for the issuing organization. That organization is
$\mathrm{org}(\mathrm{sid}(B_0))$, read from the signed session body.
Phase 5 of \cref{alg:verify} has already required the issuer's
certificate to verify under the root the verifier holds for that
organization, and to name it as its registry. So the pins consulted are
those of the organization that actually issued the session, and a
registry trusted only for some other organization cannot redirect the
lookup. Phase 6 then resolves $S$ by content
address, so by collision resistance of SHA-256 $S$ is the document the
pinned hash names. Finally it checks each link of
\cref{eq:chain-containment} explicitly, using the containment procedure
of \cref{sec:policy-subset}. Acceptance of the chain implies that every
one of these checks returned true, and by the soundness half of
\cref{prop:decidability} that implies containment in the sense of
\cref{def:subset}. The converse does not hold: by
\cref{rem:incompleteness} the verifier will also reject some chains
whose scopes are genuinely nested, so the guarantee is that accepted
chains are monotone, not that all monotone chains are accepted.
The integrity of the body content from which the policy hash and the
scopes are read is guaranteed by \cref{thm:chain-integrity}. The
first link is only as strong as the verifier's pinned set, which is an
assumption (\cref{sec:security-assumptions}) and not something the
protocol establishes.
\end{proof}

\begin{theorem}[Replay resistance]
\label{thm:replay}
A \emph{single logical verifier} maintaining a consistent,
correctly-sized nonce cache --- one cache shared across all instances
that accept chains, rather than an independent cache per replica ---
and rejecting chains whose nonce-and-invoker-key pair is already in
that cache will reject all replays within the validity window, and will
reject all chains presented after the validity window has expired.
\end{theorem}

\begin{proof}[Proof sketch]
Within the validity window, the nonce cache contains the
$(\pk_N, \text{nonce})$ pair of every previously accepted chain. A
replay presents the same pair and is rejected. Outside the validity
window, the verifier rejects on the expiry check before performing
signature verification. The cache TTL is set to the validity window
plus clock-skew tolerance, ensuring no premature eviction.
\end{proof}

\begin{theorem}[Approval binding]
\label{thm:approval-binding}
An approval receipt for invocation $I$ cannot be reused for any
invocation $I' \neq I$, and an invocation requiring approval from
service $s$ cannot be accepted with approval from service $s' \neq s$,
except with negligible probability.
\end{theorem}

\begin{proof}[Proof sketch]
The approval body signed by the approval service includes
\texttt{invocation\_digest}, a hash of the invocation body without the
approval reference itself. Modification of the invocation changes
this digest, invalidating the receipt under BLS unforgeability. The
required approval service identifiers are named by the policy $S$. The
session names $S$ by hash, but the verifier accepts the hash only if it
has pinned it for the issuing organization. $S$ is therefore a policy
the receiving organization agreed to, not one the issuer was free to
choose. Resolution is content-addressed (\cref{sec:identity-resolution}),
so no other document can be substituted behind the hash.

The requirement then propagates inward. By
\cref{thm:scope-monotonicity}, every link of the containment chain
\cref{eq:chain-containment} holds, and by the approval clause of
\cref{def:subset} each containment can only strengthen the approval
requirement. The requirement the verifier
obtains by evaluating the invocation against $\mathrm{scope}(B_{N-1})$
is therefore no weaker than the one $S$ imposes, even though the
intermediate scopes were written by the agents themselves. Routing the
approval elsewhere disturbs none of this: the policy hash is fixed at
session start and does not vary with the agent's routing choice, so a
misrouted chain arrives carrying the correct hash and the wrong receipt,
and phase 7 of \cref{alg:verify2} rejects it because no receipt signed
by a required service is present.
\end{proof}

\subsection{Threats Addressed}
\label{sec:security-threats}

The five prevented threat families of \cref{sec:threat-within-scope} are
addressed by the above theorems and the identity infrastructure of
\cref{sec:identity}, as follows. Token forgery (\threatref{1a}) is
addressed by \cref{thm:unforgeability}, and chain forgery
(\threatref{1b}) by \cref{thm:chain-integrity}. Parameter substitution
(\threatref{2a}) is addressed by \cref{thm:parameter-binding}, and scope
escalation (\threatref{2b}) by Theorems \ref{thm:chain-integrity} and
\ref{thm:scope-monotonicity} together. Cross-session replay
(\threatref{3a}) and intra-window replay (\threatref{3b}) are addressed
by \cref{thm:replay}, under the single-logical-verifier hypothesis
stated there; cross-context token reuse (\threatref{3c}) is addressed by
domain separation tags (\cref{sec:protocol-digest}). The prevented part
of the approval family (\threatref{4b}--\threatref{4d}) is addressed by
\cref{thm:approval-binding} together with the policy containment chain
of \cref{eq:chain-containment}; \threatref{4a} is bounded rather than
prevented and is discussed below. The identity family
(\threatref{5a}--\threatref{5d}) is addressed by proof-of-possession
(\cref{sec:identity-pop}), short-lived certificates and revocation
(\cref{sec:identity-revocation}), and optional transparency log
integration. Certificate substitution (\threatref{5d}) additionally
relies on the namespace binding of \cref{sec:identity-resolution}: a
certificate must verify under the root the verifier holds for the
organization its identifier names. Pinning adds an informal bound
outside the honest-root assumption. An issuer whose keys have been
compromised can still grant sessions only within the policies the
verifier has pinned for that issuer's own organization. The qualifier
depends on the namespace binding. Without it, a compromise in one
organization could draw on the policies pinned for another.

The threats of \cref{sec:threat-bounded} are bounded, not prevented.
A \emph{compromised approval service} (\threatref{4a}) can issue
receipts the human approver never authorized, and no check in
\cref{alg:verify,alg:verify2} can distinguish them from honest ones. The bound comes
from the decoupling of \cref{sec:protocol-approvals}: because approval
signatures are verified separately from the chain aggregate, the
compromise cannot extend to chain forgery or scope escalation, and it
reaches only those invocations that policy routes through the affected
service. \emph{Within-policy prompt injection} (\threatref{6a}) --- an adversary
inducing an agent to take an action that is within its permitted policy
but contrary to the principal's intent --- is not prevented by the
protocol. The protocol's contribution is to \emph{bound the blast
radius}: the adversary can cause only invocations that policy already
permits and, where policy requires human approval, will surface the
action to an approver who has an opportunity to refuse. Tightly-scoped
policies and appropriately-required approvals reduce the blast radius;
defending against prompt injection itself remains an active research
area outside the protocol's purview. \emph{Confused-deputy delegation}
(\threatref{6b}), where an agent is induced to delegate authority to an
adversary, is similarly bounded rather than prevented: the agent cannot
delegate more authority than it itself holds
(\cref{thm:scope-monotonicity}), limiting damage to the agent's own
permitted scope.

\subsection{Limitations of the Analysis}
\label{sec:security-limitations-analysis}

We emphasize that the analysis above consists of proof sketches under
specified assumptions, not machine-checked or peer-reviewed proofs.
Several aspects warrant scrutiny in any subsequent formalization.
\Cref{thm:chain-integrity} rests on the assumption that
proof-of-possession is correctly enforced at registration; an
implementation that fails to verify PoP would invalidate the chain
integrity guarantee against rogue-key attacks. \Cref{thm:replay}
depends on operational properties of the nonce cache (correct sizing,
crash recovery, distributed consistency across verifier replicas)
that are not enforced by the protocol but must be discharged by the
verifier implementation. The containment procedure of
\cref{sec:policy-subset} is sound but not complete with respect to
\cref{def:subset} (\cref{rem:incompleteness}); its soundness has been
argued informally here and would repay mechanization, since it is the
step on which \cref{thm:scope-monotonicity} rests.
Symbolic verification of the protocol in Tamarin or ProVerif would
confirm or refute these arguments and is planned future work.

\section{Discussion}
\label{sec:discussion}

This section discusses related work, limitations of the protocol and
its analysis, and directions for future work.

\subsection{Related Work}
\label{sec:related-work}

DelegationChain draws on three distinct research traditions:
capability-based authorization, pairing-based cryptographic protocols,
and agent-system security. We position our contribution relative to
each.

\paragraph{Capability-based authorization.}
The conceptual framework of attenuated capabilities, in which authority
is represented by unforgeable tokens that can be progressively
restricted as they are delegated, dates to early work on capability
operating systems and was formalized in the modern context by
\citet{miller2006robust}. The most directly relevant prior work is
Macaroons \citep{birgisson2014macaroons}, which applied attenuated
capabilities to cloud authorization using HMAC chains. A Macaroon
carries ``caveats,'' predicates that restrict its use; each delegation
appends additional caveats, and verification recomputes the HMAC chain
using a shared secret known to the verifier. Macaroons demonstrated
that attenuated delegation could be made cryptographic and efficient.
Macaroons also provide \emph{third-party caveats}, in which a caveat
names a principal other than the target service and is satisfied by a
discharge macaroon obtained from that principal
(\cref{sec:bg-capabilities}). This is the mechanism by which Macaroons
reach across trust boundaries, and any comparison that treats Macaroons
as a single-domain-only design is inaccurate. DelegationChain extends
the model in three principal directions: from shared-secret HMAC to
public-key BLS signatures; from per-hop linear signature growth to
compact aggregate signatures via BLS aggregation; and from informal
caveat languages to a typed declarative policy language with termination
and containment guarantees.

The substantive difference from third-party caveats is the shape of the
verification path rather than its reach. Discharging a third-party
caveat requires the holder to contact the named principal and collect a
discharge macaroon before presenting the token; the third party must be
available at that moment, and each additional third party adds a round
trip. DelegationChain moves that authority into signatures that the
verifier checks locally against registry-resolved public keys, so the
request path carries no discharge-collection step. The cost of this
choice is the identity infrastructure of \cref{sec:identity}, which
Macaroons does not require.

UCAN \citep{ucan-spec} also extends capability delegation to a
public-key setting, originally for Web3 contexts. UCAN uses ECDSA or
Ed25519 signatures and a JWT-like token format, with delegation
attenuation expressed through scoped capability tokens. Our work
differs from UCAN in several respects: we use BLS signatures
specifically for their aggregation property, which UCAN does not
provide; UCAN 1.0 does specify a policy language over command
arguments, but we did not find a defined containment relation between
capabilities, which is what \cref{sec:policy-subset} supplies and what
the scope monotonicity check requires; we target MCP rather than Web3 transport; and we include a
federated identity infrastructure with proof-of-possession and
revocation semantics adapted to the short-lived-credential model.

\paragraph{Authorization certificates and delegation chains.}
The problem of composing delegation chains and computing the authority
that survives composition is older than this literature. SPKI/SDSI
\citep{rfc2693} defines authorization certificates in which the
principal is a public key rather than a name, and specifies a
\emph{5-tuple reduction} algorithm that composes a chain of delegation
certificates into a single effective authorization by intersecting the
authorization tags at each step, subject to a delegation bit controlling
whether further delegation is permitted. Reduction is the direct
ancestor of the scope-monotonicity check of \cref{sec:policy-subset},
and the correspondence is close: SPKI intersects tags where we require
containment between scope expressions. The differences are that SPKI
computes the intersection, producing the resulting authority, where our
verifier only checks a containment relation that the delegator has
already asserted; that SPKI's tag \emph{*-forms} (prefix, range, set)
are a fixed and deliberately small constraint vocabulary, where our
policy language is typed and admits conditions over named parameter
paths; and that SPKI has no notion of signature aggregation.

X.509 proxy certificates \citep{rfc3820} apply the same idea within Web
PKI and were deployed at scale in grid computing. An end-entity
certificate signs a short-lived proxy certificate, which may itself sign
another, producing a delegation chain that a relying party validates as
an ordinary X.509 path; attenuation is expressed through an embedded
\texttt{ProxyCertInfo} policy field. This is the closest classical prior
art to the certificate-chain-plus-policy design of \cref{sec:identity}.
Two differences are worth naming. RFC 3820 leaves the content of the
policy field opaque --- it names a policy language by OID and carries
its bytes, without specifying one --- so nothing in the standard
provides the decidable containment check our \cref{sec:policy} is built
around. And proxy certificate chains root in a CA hierarchy, where our
registry model is federated and explicitly declines a global trust
anchor (\cref{sec:identity-federated}).

Biscuit \citep{biscuit-spec} is the closest contemporary system in the
capability-token line. Biscuit tokens are public-key verifiable, support
offline attenuation --- a holder may append a block of additional checks
at any time, restricting the token without contacting the issuer, and
cannot remove a block without invalidating the signature --- and carry
an authorization language based on a purpose-built Datalog with
specified evaluation semantics. Biscuit's Datalog is more expressive
than our policy language, and its formal treatment of evaluation is more
developed than the sketch we give. The differences run the other way on
two axes: Biscuit signs each block individually with Ed25519 or ECDSA
and does not aggregate, so token size grows with attenuation depth; and
Biscuit does not bind a token to a specific invocation's parameter
values, since attenuation constrains future use rather than committing
to one call. We regard Biscuit's Datalog as the more serious policy
design and note that a containment check over it would be a
substantially harder problem than the one \cref{prop:decidability}
addresses.

ZCAP-LD \citep{zcapld}, developed in the W3C Credentials Community
Group, expresses object capabilities as linked-data documents with
invocation and delegation proofs, and shares the attenuated-delegation
model. It remains a community-group draft rather than a standard, and
its caveat vocabulary is extensible rather than fixed, which places it
outside the decidability constraints of \cref{sec:policy}.

\paragraph{Proof-carrying authorization.}
A separate tradition places the burden of justifying access on the
requester. \citet{appel1999pca} introduced proof-carrying
authentication, in which a request arrives accompanied by a proof, in a
higher-order logic, that it is authorized; the verifier need only check
the proof, and the framework is expressive enough to encode Taos, SPKI,
SDSI and X.509. \citet{bauer2003pca} developed the approach into a
deployed system for web access control. The comparison is instructive
because the trust structure is the same as ours --- the verifier checks
locally, without consulting the issuer --- while the mechanism is the
opposite: proof-carrying authorization gains expressiveness by admitting
an arbitrary logic and pushing proof search to the requester, where we
give up expressiveness (\cref{sec:policy-limitations}) to keep the
verifier's work bounded by a syntactic check. A DelegationChain chain
can be read as a very restricted proof, in which the only inference
rules are signature verification and scope containment.

\paragraph{Cryptographic infrastructure.}
The BLS signature scheme is due to \citet{boneh2001bls}. Aggregate
signature security under proof-of-possession is analyzed by
\citet{boneh2018compact}, whose work motivates our PoP requirement
during registration. We use the signing variant standardized by the
CFRG \citep{ietf-bls-signature}, the BLS12-381 curve parameters of
\citet{ietf-pairing-curves}, and the hash-to-curve construction of
RFC 9380 \citep{rfc9380}.

The problem our chain digest solves --- producing a single compact
signature over an \emph{ordered} sequence of signers on distinct
messages, such that the order is itself authenticated --- is the problem
that \emph{sequential aggregate signatures} were introduced to solve.
\citet{lmrs2004seqagg} gave the first construction, in which each signer
folds its signature into the aggregate it receives from its predecessor,
using certified trapdoor permutations; the order of signing is bound by
the construction itself. \citet{boldyreva2007ordered} extended the line
to ordered multisignatures and identity-based sequential aggregates in
the pairing setting. We should therefore be precise about what is and is
not new here. Ordered, aggregated signature chains are not new, and we
do not claim them.

What we do claim is narrower: a specification of how to obtain order
binding for delegation chains using a recursive hash chain over
domain-separated token bodies together with \emph{plain} BLS
aggregation, rather than a dedicated sequential aggregate scheme. The
reason for the choice is practical rather than theoretical. The
construction needs no trapdoor permutations and no scheme-specific
sequential signing operation; it uses the ordinary signing and
aggregation operations of the CFRG BLS draft
\citep{ietf-bls-signature}, so it can be built on any conforming
library, and the order binding lives in data the verifier already has to
hash. What we give up is that the hash chain must be recomputed by the
verifier from the received bodies, whereas a native sequential aggregate
carries order binding inside the signature object. Whether that trade is
worth making is an empirical question about verification cost, which
this paper does not settle. Certificate Transparency \citep{rfc9162}
provided the model for our optional transparency log integration.

\paragraph{MCP and agent-system security.}
The security gap in cross-organizational MCP deployments has been
empirically characterized by recent measurement work.
\citet{zhou2026mcpauth} surveyed 7,973 live remote MCP servers and found
40.55\% exposing tools without authentication; of the OAuth-enabled
servers they were able to probe actively, every one exhibited at least
one authentication flaw, and the disclosure process yielded nine CVE
identifiers. \citet{maloyan2026breaking} identify additional
protocol-level vulnerabilities in MCP. These works establish the problem
but do not propose cryptographic solutions. Single-organization runtime
enforcement approaches \citep{buhler2026agentbound} provide
defense-in-depth within an organization's perimeter but do not
provide cross-organizational cryptographic proofs and are not
designed to extend across organizational boundaries.

The closest contemporary work is the Agent Identity Protocol of
\citet{prakash2026aip}, which proposes invocation-bound capability
tokens for cross-protocol agent delegation. AIP and DelegationChain
share the high-level goal of providing verifiable invocation
authorization in agent settings. The principal differences are:
DelegationChain provides BLS-based aggregate signatures over
multi-hop chains, where AIP relies on individual signatures per hop;
DelegationChain specifies a formal policy expression language with a
proof of evaluator termination and a soundness proof for its scope
containment check, where AIP's policy semantics are less formally
treated; and DelegationChain includes a complete federated identity
infrastructure specification, where AIP focuses on the token
construction. The two designs are largely complementary, and either
could be adopted in deployments depending on the priority placed on
aggregate-signature compactness versus simplicity of individual
signature verification.

\paragraph{Workload and identity infrastructure.}
SPIFFE/SPIRE \citep{spiffe} provides workload identity through
short-lived X.509 certificates and JWT-format SVIDs. While SPIFFE
addresses workload identity within a trust domain, it does not
provide parameter-bound authorization, delegation chain integrity,
or aggregate signatures. OAuth 2.1 \citep{oauth21} addresses caller
identity and scope but requires synchronous token introspection on the
verification path and does not provide parameter binding. We view
DelegationChain not as a replacement for these systems but as
complementary infrastructure for the specific use case of verifiable
agent-to-tool invocation across organizations.

\emph{no anchor} because the target service must hold its own root
secret, while third-party caveats require no secret shared with the
third party; it is \tpart{} on \emph{offline} for the same reason, since
discharging a third-party caveat costs a round trip. SPKI/SDSI is
\tpart{} on \emph{parameter binding} because authorization tags
constrain values through \texttt{*}-forms without binding a certificate
to one invocation's exact parameters. X.509 proxy certificates are
\tunspec{} on parameter binding because RFC 3820 names a policy language
by OID and carries its bytes without specifying one, and \tpart{} on
offline because path validation is local while revocation checking is
not. Biscuit is \tno{} on parameter binding because attenuation
constrains future use rather than committing to a single call. SPIFFE is
\tpart{} on \emph{no anchor} because cross-domain use requires SPIFFE
Federation. OAuth 2.1 is \tpart{} on offline because a JWS access token
verifies locally while introspection does not. AIP is \tunspec{} on
offline because the source does not state it. DelegationChain is
\tpart{} on offline for the reasons given in \cref{sec:limitations}.

\subsection{Limitations}
\label{sec:limitations}

We discuss limitations of the work along several dimensions.

\paragraph{Analytical, not empirical.}
This paper presents a protocol design and preliminary security
analysis. It does not present empirical performance measurements from
a reference implementation. The verification cost analysis of
\cref{sec:protocol-verification} is based on counting cryptographic
operations and library-reported costs for those operations; precise
wall-clock latency in the deployment configurations of interest will
depend on implementation choices (BLS library, multi-pairing strategy,
deserialization performance) that this paper does not commit to.
A Rust reference implementation using the \texttt{blst} library is
under development, and the empirical evaluation described in
\cref{sec:future-work} is in progress.

\paragraph{Offline verification is qualified.}
We claim verification that requires no synchronous call to the issuing
authority \emph{on the dominant path}, and the qualification is load
bearing. Two dependencies remain, and a third can be avoided.
Certificate resolution (\cref{sec:identity-resolution}) queries the
issuing registry on a cache miss. Revocation
(\cref{sec:identity-revocation}) requires polling, push, or log
monitoring, which is a continuous background dependency rather than a
per-request one. Policy resolution is the avoidable one. Pinned
policies can be fetched when they are pinned
(\cref{sec:identity-resolution}), and only a verifier that defers the
fetch to first use pays a round trip, on that call. In the steady state --- a partner whose
certificates and policies are already cached --- verification touches
none of these and is genuinely local. On a cold cache it is not, and
statements elsewhere in this paper about offline verification should be
read with that scope.

The obvious repair is to carry certificates in the chain, as X.509 does,
so that a verifier needs the registry root key but not the registry.
This would make verification offline modulo revocation, and we note it
as a deployment option rather than adopting it, because the arithmetic
is unfavourable in exactly the dimension the design optimizes. A
certificate carries a 48-byte public key and a 96-byte registry
signature before any identifier, timestamp, or serial-number field, so
attaching one per hop necessarily costs more per hop than the 96 bytes
that aggregation saves across the whole chain. A design that carried
certificates inline would be giving up the bandwidth argument for
aggregation in order to buy offline verification, and it is not obvious
which of the two a deployment should prefer. Settling it requires the
measurements described in \cref{sec:future-work}, not further argument
here.

\paragraph{Security arguments are sketches, not proofs.}
\Cref{sec:security} presents proof sketches that reduce protocol
security to standard cryptographic assumptions. These sketches have
not been mechanized in a proof assistant nor have they been verified
by independent cryptographer review. Symbolic protocol verification
using Tamarin or ProVerif is planned and is expected to reveal at
minimum the kind of subtle interaction issues that hand-analysis
typically misses (e.g., key-compromise impersonation paths, unknown
key-share variants). We treat the current analysis as a starting
point for formal verification, not as a substitute for it.

\paragraph{Policy language expressiveness.}
The policy language of \cref{sec:policy} is deliberately bounded. It
cannot express semantic conditions requiring evaluation by an LLM or
external system (``is this email professional?''), stateful
conditions referring to data outside the invocation (``is this user
under their monthly limit?''), or conditions requiring synchronous
queries to external systems. These limitations are intentional: each
relaxation would compromise the decidability, termination, or
side-effect-freedom guarantees on which the security analysis depends.
Where richer policy expressions are required in practice, we
anticipate them being enforced at the tool implementation layer
\emph{after} the protocol's stateless check has succeeded. A
fully-integrated treatment of stateful policy may require extensions
to the protocol --- including verifiable LLM attestation for
semantic conditions --- which we leave as future work.

\paragraph{Threat model boundaries.}
Several classes of threats are explicitly out of scope
(\cref{sec:threat-outside}), including fully-compromised HSMs,
compromised signing service infrastructure, side-channel attacks,
and attacks on human approvers' devices. The protocol provides no
defense against these and relies on operational measures (HSM
hardening, key custody discipline, secure approver workflows) for
mitigation. Within-policy prompt injection is bounded but not
prevented (\cref{sec:security-threats}); the protocol's contribution
is to ensure that prompt-injected agents cannot exceed their permitted
policy, not to prevent prompt injection itself.

\paragraph{Post-quantum security.}
BLS12-381 is not post-quantum secure. A sufficiently capable quantum
adversary could forge BLS signatures. Migration to a post-quantum
signature scheme is a future protocol version; this likely involves
hybrid construction combining BLS with a post-quantum scheme during
a transition period, with the complexity tradeoffs that hybrid
constructions imply.

\paragraph{Bootstrapping and adoption.}
The federated registry model requires both communicating organizations
to operate compatible registries (or to participate in a shared
transparency log). Adoption of the protocol in cross-organizational
agent ecosystems thus faces a bootstrapping problem: early adopters
have limited peers to communicate with, and the value of adoption
grows with peer density. We do not address bootstrapping strategies
in this paper, but observe that the same dynamic affects all
cross-organizational identity protocols, including SPIFFE and
SAML federation. Successful adoption is likely to require either
integration into a widely-deployed platform (e.g., as a feature of
an MCP-compliant agent framework) or coordination through standards
bodies.

\subsection{Future Work}
\label{sec:future-work}

We identify several directions for future work, in approximate order
of priority.

\emph{Reference implementation and empirical evaluation.} A Rust
reference implementation using \texttt{blst} is the most immediate
next step. Empirical evaluation should measure end-to-end verification
latency across chain lengths, throughput under load, and storage
overhead for nonce caches and certificate caches. Comparison with
OAuth token introspection and SPIFFE SVID verification on
representative workloads will substantiate the analytical cost
arguments of \cref{sec:protocol-verification}.

\emph{Symbolic verification.} Modeling the protocol in Tamarin or
ProVerif and proving the security properties of \cref{sec:security}
will validate (or, more usefully, falsify) the hand-written proof
sketches. This is expected to surface protocol details requiring
revision before publication of a normative specification.

\emph{Differential privacy on audit trails.} The protocol generates
detailed audit records of every accepted invocation. For deployments
in regulated industries, the ability to produce compliance attestations
(``$X\%$ of invocations were authorized'') without exposing the
content of individual invocations would have practical value.
Standard differential privacy mechanisms apply; their integration into
the protocol's audit format is straightforward but was deferred from
this work for scope reasons.

\emph{Verifiable LLM attestation for semantic policy conditions.}
The most significant restriction of the policy language is its
inability to express semantic conditions. Recent work on verifiable
LLM inference (zkML and related approaches) may enable a future
extension in which semantic policy conditions are evaluated by an LLM
whose evaluation is itself cryptographically attested. This is
speculative; the practicality of zkML at the latencies required for
authorization protocols is not currently established.

\emph{Post-quantum migration.} As discussed above, planning for
migration to post-quantum signatures is appropriate even before the
threat is acute. Investigating hybrid BLS-plus-post-quantum
constructions adapted to the aggregation property is an open question.

\emph{Cross-registry naming and discovery.} This paper does not
address how organizations choose and namespace their
\texttt{organization-id} values. In practice deployments will use
DNS-style hierarchical naming or other conventions, but standardizing
this is needed before adoption at scale.

\section{Conclusion}
\label{sec:conclusion}

The growing deployment of LLM-based agents across organizational
boundaries creates an authorization problem that existing protocols do
not adequately address. Receiving organizations need cryptographic
assurance that an incoming tool invocation was authorized by a
specific agent operating within a specific scope on behalf of specific
principals, with specific parameter values --- and they need this
assurance without depending on the sending organization's
infrastructure being trustworthy at verification time, and, so far as
possible, without depending on its being reachable either.

We have presented DelegationChain, a protocol combining
cross-organizational verification without a shared trust anchor,
parameter-bound authorization, and aggregatable proof chains, with
verification that is local in the steady state. That last property is
qualified rather than absolute: certificate resolution touches the
issuing registry on a cache miss, policy resolution does too unless
policies are fetched when they are pinned, and revocation is a standing
background dependency (\cref{sec:limitations}). The protocol's cryptographic
core is a recursive chain digest construction over BLS12-381
aggregate signatures, with proof-of-possession-protected registration
defending against rogue-key attacks. The associated policy expression
language is terminating and side-effect-free by construction, and
admits a polynomial-time containment check that is sound with respect
to its semantic subset relation, supporting the verifier's scope
monotonicity check without introducing computational or semantic
hazards. The federated
identity infrastructure permits interoperation between mutually
distrusting organizations through direct peering, federated
transparency logs, or hierarchical attestation, as deployment context
requires.

We have stated and sketched proofs of the protocol's core security
properties --- unforgeability, parameter binding, chain integrity,
scope monotonicity, replay resistance, and approval binding --- and
mapped these to the threat model. We have been explicit about the
threats the protocol does not address, particularly within-policy
prompt injection, which the protocol bounds rather than prevents.

The work has clear limitations: the analysis is hand-written rather
than mechanically verified, no empirical performance data is yet
available, and several threat classes remain out of scope. A
reference implementation in Rust, symbolic verification in Tamarin
or ProVerif, and empirical evaluation are the immediate next steps.
These additions would establish DelegationChain as a viable
foundation for the inter-agent authorization layer in production
deployments.

We view this paper as a starting point. The design space for
cross-organizational agent authorization is still being mapped, and
multiple competing proposals --- AIP and AgentBound among them ---
are appearing simultaneously with this work. We expect
useful integration and competition between these proposals over the
next several years as the inter-agent ecosystem matures. Our
contribution is one design point in this space, optimized for
combining attenuated capability semantics, public-key
cross-organizational verification, and aggregate-signature
efficiency. Whether this combination proves to be the right one for
the deployments that emerge is a question only the deployments will
answer.
